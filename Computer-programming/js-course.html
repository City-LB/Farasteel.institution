PART I

JavaScript Fundamentals

Chapter 1

Introduction to JavaScript

JavaScript is a lightweight, interpreted programming language that runs in every modern web browser and, thanks to runtimes like Node.js, on servers and command lines as well. It is one of the three core technologies of the web, alongside HTML (structure) and CSS (presentation). Where HTML builds the skeleton of a page and CSS dresses it, JavaScript gives it behavior: it responds to clicks, validates forms, updates content without reloading the page, fetches data from servers, and drives entire applications.

JavaScript is a high-level language (you don't manage memory by hand), dynamically typed (a variable's type is decided at runtime, not declared up front), and multi-paradigm (you can write it in a procedural, object-oriented, or functional style). It is also single-threaded with an event loop, which lets it handle many operations — timers, network requests, user input — without blocking.

console.log("Hello, JavaScript!");

That one line already shows the essentials of the language: a built-in object (console), a method call (.log()), and a string literal passed as an argument.

Where JavaScript runs

  • Browsers — every major browser has a JavaScript engine (Chrome/Edge use V8, Firefox uses SpiderMonkey, Safari uses JavaScriptCore).
  • Servers — Node.js and Deno let JavaScript run outside the browser, powering APIs and command-line tools.
  • Mobile & desktop apps — frameworks like React Native and Electron use JavaScript to build native-feeling apps.
Teaching note: Have students open their browser's DevTools console (F12 or Right-click → Inspect → Console) and type a few expressions before writing any files. Seeing instant output builds confidence early.
Chapter 2

History and Evolution of JavaScript

JavaScript was created in 1995 by Brendan Eich at Netscape, reportedly in just ten days. It was originally called Mocha, then LiveScript, and was renamed JavaScript as a marketing move to ride the popularity of Java — despite the two languages being fundamentally different.

To prevent fragmentation across browsers, JavaScript was standardized in 1997 under the name ECMAScript (ES) by Ecma International. Browser vendors implement ECMAScript; "JavaScript" is the popular name for that implementation.

Key milestones

  • ES3 (1999) — regular expressions, try/catch, widely supported for a decade.
  • ES5 (2009) — strict mode, JSON support, array methods like map and filter.
  • ES6 / ES2015 — the biggest update ever: let/const, arrow functions, classes, promises, template literals, modules, destructuring.
  • ES2016–present — yearly releases adding features like async/await (2017), optional chaining (2020), and top-level await (2022).

Node.js (2009) extended JavaScript beyond the browser, and today JavaScript is consistently ranked among the most widely used programming languages in the world.

Chapter 3

Setting Up Your Development Environment

You need very little to start writing JavaScript: a text editor and a browser. As you progress, a few extra tools make development faster and more professional.

Minimum setup

  • A code editor — Visual Studio Code is the industry standard, free, with excellent JavaScript support.
  • A modern browser with developer tools — Chrome, Edge, or Firefox.

Linking JavaScript to HTML

<!-- Inline script -->
<script>
  console.log("Hello from inline JS");
</script>

<!-- External file (preferred) -->
<script src="script.js" defer></script>

The defer attribute tells the browser to keep parsing the HTML and only run the script once the page has finished loading, which avoids errors from scripts trying to access elements that don't exist yet.

Installing Node.js

Node.js lets you run JavaScript from the command line, outside a browser. Download the LTS (Long-Term Support) version from nodejs.org, then confirm the install:

node --version
npm --version

npm (Node Package Manager) ships with Node and is used to install third-party libraries.

Teaching note: Have each student create a folder with an index.html and a script.js, link them with <script src="script.js" defer></script>, and confirm a console.log message appears in DevTools before moving on.
Chapter 4

How JavaScript Works

Understanding what happens when JavaScript runs makes debugging and advanced topics (like closures and asynchronous code) far easier later.

The JavaScript engine

Every browser has a JavaScript engine (e.g. V8) that takes your code through roughly these stages: parsing (turning source text into a syntax tree), compiling (V8 uses just-in-time compilation to turn code into fast machine code), and execution.

The call stack

JavaScript executes using a single call stack: a "last in, first out" structure that tracks which function is currently running. When a function is called, a new frame is pushed onto the stack; when it returns, the frame is popped off.

function greet() {
  sayHi();
}
function sayHi() {
  console.log("Hi!");
}
greet(); // greet() is pushed, then sayHi() is pushed, then sayHi() returns and is popped, then greet() returns

The event loop

Because there is only one call stack, JavaScript is single-threaded — it can only do one thing at a time. Yet it can handle timers, user clicks, and network requests without freezing the page. This is done through the event loop, which works with two extra pieces:

  • Web APIs / Node APIs — provided by the browser or Node, they handle things like setTimeout or network calls in the background.
  • Callback/task queue — when a background task finishes, its callback is placed in a queue.

The event loop constantly checks: is the call stack empty? If so, it takes the next item from the queue and pushes it onto the stack to run. This is why code inside setTimeout(fn, 0) still runs after all synchronous code, no matter how small the delay.

Teaching note: This chapter is easier to teach after Chapter 18 (Error Handling) is revisited alongside Promises in a later course. A simple diagram of Call Stack → Web APIs → Callback Queue → Event Loop is worth drawing on a whiteboard.
Chapter 5

JavaScript Syntax

Syntax is the set of rules that defines correctly structured JavaScript. Getting comfortable with it early prevents a lot of frustrating errors later.

Statements and semicolons

A JavaScript program is a sequence of statements, usually ending in a semicolon.

let name = "Ada";
console.log(name);

JavaScript has "automatic semicolon insertion," which can insert semicolons for you — but relying on it can cause subtle bugs, so most style guides recommend always writing them explicitly.

Case sensitivity

myVariable and MyVariable are two different identifiers. JavaScript is fully case-sensitive, including keywords (true is valid, True is not).

Whitespace and blocks

Whitespace (spaces, tabs, newlines) is generally ignored between tokens, letting you format code for readability. Curly braces { } group statements into a block:

if (true) {
  console.log("inside a block");
}

Identifiers

Variable and function names can contain letters, digits, $, and _, but cannot start with a digit, and cannot be a reserved word like let or class.

Teaching note: Introduce a consistent naming convention early — camelCase for variables/functions, PascalCase for classes — so students build good habits before bad ones form.
Chapter 6

Comments

Comments are notes in the source code that JavaScript ignores when it runs. They exist entirely for humans: to explain why code does something, document assumptions, or temporarily disable a line while debugging.

Single-line comments

// This calculates the area of a circle
const area = Math.PI * radius * radius;

Multi-line comments

/*
  This function validates a user's email address.
  It returns true if valid, false otherwise.
*/
function isValidEmail(email) { /* ... */ }

Good commenting practice

  • Comment on why, not what — the code already shows what it does; a good comment explains reasoning that isn't obvious from the code itself.
  • Keep comments up to date — a stale comment that contradicts the code is worse than no comment.
  • Avoid over-commenting simple, self-explanatory code.
Chapter 7

Variables

A variable is a named container for a value. JavaScript has three ways to declare one: var, let, and const.

var a = 1;   // old style, function-scoped
let b = 2;   // modern, block-scoped, reassignable
const c = 3; // modern, block-scoped, cannot be reassigned

let vs const

Use const by default — it signals that a value shouldn't be reassigned, making code easier to reason about. Use let only when you know the value needs to change (like a loop counter). Note that const prevents reassignment, not mutation: the contents of an array or object declared with const can still change.

const scores = [10, 20];
scores.push(30); // allowed — we're mutating, not reassigning
scores = [];      // TypeError: Assignment to constant variable.

Why avoid var

var is function-scoped rather than block-scoped, and it is "hoisted" with an initial value of undefined (see Chapter 15), which can lead to confusing bugs. Modern JavaScript style guides recommend using let and const exclusively.

Naming rules and conventions

  • Must start with a letter, $, or _.
  • Case-sensitive; cannot be a reserved word.
  • Convention: camelCase for variables (userAge), UPPER_SNAKE_CASE for constants that represent fixed configuration (MAX_RETRIES).
Chapter 8

Data Types

JavaScript has two categories of data types: primitives and objects.

Primitive types

  • String — text, e.g. "hello"
  • Number — all numbers, integer or decimal, e.g. 42, 3.14
  • Boolean — true or false
  • undefined — a variable that has been declared but not assigned a value
  • null — an intentional absence of any value
  • BigInt — integers larger than Number can safely represent, e.g. 123n
  • Symbol — a unique, immutable value often used as an object property key

The Object type

Everything that isn't a primitive is an object — including plain objects, arrays, functions, and dates. Objects are collections of key/value pairs and are covered in depth in Part III.

Checking a type

typeof "hello";     // "string"
typeof 42;          // "number"
typeof true;        // "boolean"
typeof undefined;   // "undefined"
typeof null;        // "object"  (a famous, long-standing JS quirk)
typeof {};           // "object"
typeof [];           // "object"  (arrays are objects)
typeof function(){}; // "function"
Teaching note: The typeof null === "object" quirk dates back to JavaScript's original 1995 implementation and is kept for backward compatibility. It's a great "fun fact" moment for students.
Chapter 9

Operators

Operators let you combine, compare, and manipulate values.

Arithmetic operators

5 + 2;   // 7   addition
5 - 2;   // 3   subtraction
5 * 2;   // 10  multiplication
5 / 2;   // 2.5 division
5 % 2;   // 1   remainder (modulo)
5 ** 2;  // 25  exponentiation

Assignment operators

let x = 5;
x += 3; // x = x + 3 -> 8
x -= 2; // 6
x *= 2; // 12
x /= 4; // 3

Comparison operators

5 == "5";   // true  (loose equality, converts types)
5 === "5";  // false (strict equality, no conversion)
5 != "5";   // false
5 !== "5";  // true
5 > 2; 5 < 2; 5 >= 5; 5 <= 4;

Always prefer === and !== over == and !=. Strict equality avoids the surprising type coercion covered in Chapter 10.

Logical operators

true && false; // false (AND)
true || false; // true  (OR)
!true;         // false (NOT)

Other useful operators

  • Ternary: const label = age >= 18 ? "adult" : "minor";
  • Nullish coalescing (??): const name = input ?? "Anonymous"; — returns the right side only if the left is null or undefined.
  • Optional chaining (?.): user?.address?.city — safely reads a nested property without throwing if something along the chain is missing.
Chapter 10

Type Conversion

JavaScript is dynamically and loosely typed, meaning it will often convert values between types automatically — this is called type coercion. Understanding it explicitly prevents a huge number of common bugs.

Implicit conversion

"5" + 2;    // "52"  (number converted to string)
"5" - 2;    // 3     (string converted to number)
"5" * "2";  // 10
true + 1;   // 2     (true becomes 1)
"5" == 5;   // true  (loose equality coerces)

The + operator is special: if either operand is a string, it performs string concatenation; otherwise, it performs numeric addition. Other arithmetic operators (-, *, /) always try to convert to numbers.

Explicit conversion

String(123);     // "123"
Number("123");   // 123
Number("abc");   // NaN
Boolean(0);      // false
Boolean("");     // false
Boolean("hi");   // true
parseInt("42px"); // 42
parseFloat("3.14m"); // 3.14

Truthy and falsy values

When a value is used where a boolean is expected (like an if condition), JavaScript converts it. There are only eight falsy values: false, 0, -0, 0n, "", null, undefined, and NaN. Everything else — including "0", [], and {} — is truthy.

Teaching note: The rule "always use ===" mostly exists because of the surprises in this chapter. Show [] == false (true!) as a cautionary example of why loose equality is risky.

Program Flow

Chapter 11

Conditional Statements

Conditionals let a program make decisions and run different code depending on circumstances.

if / else if / else

const hour = 14;
if (hour < 12) {
  console.log("Good morning");
} else if (hour < 18) {
  console.log("Good afternoon");
} else {
  console.log("Good evening");
}

switch

A switch is useful when comparing one value against several possibilities.

const day = "Mon";
switch (day) {
  case "Sat":
  case "Sun":
    console.log("Weekend");
    break;
  default:
    console.log("Weekday");
}

The break keyword stops execution from "falling through" into the next case — a common source of bugs for beginners when forgotten.

Ternary operator as a compact conditional

const status = age >= 18 ? "adult" : "minor";
Teaching note: Have students trace through a multi-branch if/else if by hand before running it, predicting the output, to build the habit of reading conditionals carefully.
Chapter 12

Loops

Loops repeat a block of code while a condition holds, avoiding repetitive code.

for

for (let i = 0; i < 5; i++) {
  console.log(i);
}

while and do...while

let count = 0;
while (count < 3) {
  console.log(count);
  count++;
}

let n = 0;
do {
  console.log(n);
  n++;
} while (n < 3); // runs at least once, even if the condition is false

for...of and for...in

const fruits = ["apple", "banana", "cherry"];
for (const fruit of fruits) {
  console.log(fruit); // iterates over values
}

const person = { name: "Ada", age: 30 };
for (const key in person) {
  console.log(key, person[key]); // iterates over keys
}

Use for...of for arrays and other iterables (you get the values directly); use for...in for plain objects (you get the keys).

break and continue

for (let i = 0; i < 10; i++) {
  if (i === 3) continue; // skip this iteration
  if (i === 6) break;    // stop the loop entirely
  console.log(i);
}
Teaching note: Infinite loops are a rite of passage. Show one deliberately (while (true) {}) in a sandboxed environment and explain how to stop a runaway script.
Chapter 13

Functions

A function is a reusable block of code that performs a task, optionally taking inputs (parameters) and producing an output (a return value).

Function declarations

function add(a, b) {
  return a + b;
}
add(2, 3); // 5

Function expressions and arrow functions

const multiply = function (a, b) {
  return a * b;
};

const square = (n) => n * n;             // implicit return
const greet = (name) => {                  // explicit return
  return `Hello, ${name}`;
};

Arrow functions are shorter and, importantly, do not have their own this binding — they inherit this from the surrounding scope, which is often exactly what you want in callbacks.

Default and rest parameters

function power(base, exponent = 2) {
  return base ** exponent;
}
power(4); // 16 (exponent defaults to 2)

function sum(...numbers) {
  return numbers.reduce((total, n) => total + n, 0);
}
sum(1, 2, 3, 4); // 10

Functions as first-class values

In JavaScript, functions can be stored in variables, passed as arguments, and returned from other functions — this makes patterns like callbacks and higher-order functions possible.

function applyTwice(fn, value) {
  return fn(fn(value));
}
applyTwice(square, 3); // 81
Chapter 14

Scope

Scope determines where in your code a variable is accessible.

Global scope

Variables declared outside any function or block are in the global scope and can be accessed from anywhere.

Function scope

Variables declared with var inside a function are only visible inside that function.

Block scope

let and const are block-scoped: they only exist within the nearest pair of curly braces { }, whether that's an if statement, loop, or standalone block.

if (true) {
  let x = 10;
  var y = 20;
}
console.log(y); // 20 — var leaked out of the block
console.log(x); // ReferenceError: x is not defined

Lexical scope and nested functions

JavaScript uses lexical scoping: a function can access variables from the scope it was defined in, not the scope it's called from.

function outer() {
  const message = "Hi from outer";
  function inner() {
    console.log(message); // inner can see outer's variables
  }
  inner();
}

This nested-scope behavior is the foundation for closures, covered next.

Chapter 15

Hoisting

Hoisting is JavaScript's behavior of processing variable and function declarations before executing any code, effectively "moving" declarations to the top of their scope during compilation.

var hoisting

console.log(a); // undefined (not an error!)
var a = 5;

The declaration var a is hoisted to the top of the scope, but the assignment a = 5 stays where it is. So at the point of the console.log, a exists but is undefined.

let and const hoisting: the Temporal Dead Zone

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 5;

let and const are also hoisted, but they remain in a "Temporal Dead Zone" from the start of the block until their declaration is reached, and accessing them there throws an error. This is generally considered safer behavior than var's silent undefined.

Function hoisting

sayHi(); // works! "Hi there"
function sayHi() {
  console.log("Hi there");
}

Function declarations are fully hoisted, body and all, so they can be called before their definition appears in the code. Function expressions (including arrow functions assigned to a variable) are not — only the variable declaration is hoisted, following the same rules as var/let/const.

Chapter 16

Closures

A closure is formed when a function "remembers" the variables from the scope in which it was created, even after that outer scope has finished executing. This is one of JavaScript's most powerful and distinctive features.

function makeCounter() {
  let count = 0;
  return function () {
    count++;
    return count;
  };
}

const counter = makeCounter();
counter(); // 1
counter(); // 2
counter(); // 3

Each time makeCounter is called, it creates a new, private count variable. The returned inner function keeps access to that specific count through a closure, even though makeCounter has already returned. This is how you get private state in JavaScript without classes.

Practical uses of closures

  • Data privacy — expose only the functions that touch a variable, keeping the variable itself inaccessible from outside.
  • Function factories — functions that generate other, specialized functions.
  • Callbacks and event handlers — a callback often needs to "remember" data from when it was set up.
function multiplierFactory(factor) {
  return (n) => n * factor;
}
const double = multiplierFactory(2);
const triple = multiplierFactory(3);
double(5); // 10
triple(5); // 15
Teaching note: Closures click for most students once they build the counter example themselves and add a reset() function alongside increment(), sharing the same private count.
Chapter 17

Recursion

Recursion is when a function calls itself to solve a smaller version of the same problem, until it reaches a base case that stops the recursion.

function factorial(n) {
  if (n <= 1) return 1;        // base case
  return n * factorial(n - 1); // recursive case
}
factorial(5); // 120

Anatomy of a recursive function

  • Base case — the condition that stops the recursion; without it, the function calls itself forever and crashes with a stack overflow.
  • Recursive case — the function calls itself with input that moves closer to the base case.

A classic example: Fibonacci

function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
fib(6); // 8

Recursion vs. loops

Anything recursion can do, a loop can also do, and vice versa. Recursion tends to produce more elegant, readable code for naturally recursive problems (like traversing trees or nested data), but it uses more memory (the call stack) and can be slower than an equivalent loop for simple cases.

Teaching note: Trigger a real RangeError: Maximum call stack size exceeded deliberately by omitting a base case, so students see what happens and understand why the base case matters.
Chapter 18

Error Handling

Errors are inevitable — invalid input, failed network requests, bugs. JavaScript provides try...catch to handle errors gracefully instead of letting them crash the program.

try {
  const result = JSON.parse("this is not valid JSON");
} catch (error) {
  console.log("Something went wrong:", error.message);
} finally {
  console.log("This always runs, error or not");
}

Throwing your own errors

function withdraw(balance, amount) {
  if (amount > balance) {
    throw new Error("Insufficient funds");
  }
  return balance - amount;
}

try {
  withdraw(100, 200);
} catch (error) {
  console.log(error.message); // "Insufficient funds"
}

Built-in error types

  • Error — generic base error type.
  • TypeError — an operation on the wrong type, e.g. calling something that isn't a function.
  • RangeError — a value is outside an allowed range, e.g. infinite recursion.
  • ReferenceError — referring to a variable that doesn't exist.
  • SyntaxError — invalid code structure, usually caught before the code even runs.

Error handling in asynchronous code

With Promises, errors are handled with .catch(); with async/await, the same try...catch pattern works directly on awaited calls.

Chapter 19

Strict Mode

"use strict" switches JavaScript into a stricter variant that catches common mistakes, throws errors for unsafe actions, and disables some confusing features.

"use strict";

x = 10; // ReferenceError: x is not defined (without strict mode, this would silently create a global variable)

What strict mode changes

  • Prevents accidental creation of global variables from unassigned variables.
  • Throws errors for assignments that would otherwise fail silently (e.g. assigning to a read-only property).
  • Disallows duplicate parameter names in functions.
  • Makes this undefined in regular functions called without an object, instead of defaulting to the global object.

How to enable it

// At the top of a file, applies to the whole file
"use strict";

// Or at the top of a function, applies to that function only
function myFunction() {
  "use strict";
  // ...
}

Modules and classes are automatically in strict mode, so most modern JavaScript (written with ES modules) doesn't need the directive explicitly — but it's important to understand for reading and maintaining older code.

Chapter 20

Debugging JavaScript

Debugging is the process of finding and fixing problems in code. Good debugging skills often matter more than memorizing syntax.

console methods

console.log("basic message");
console.warn("a warning");
console.error("an error");
console.table([{ name: "Ada", age: 30 }, { name: "Bo", age: 25 }]);
console.time("loop");
// ...code...
console.timeEnd("loop"); // measures how long the code took

Browser DevTools

  • Breakpoints — click a line number in the Sources panel to pause execution there and inspect variables.
  • The debugger statement — placing debugger; in your code pauses execution at that point whenever DevTools is open.
  • Watch expressions and the call stack panel — inspect values and see exactly how the current function was reached.

Reading error messages

An error message usually names the error type, a description, and a file/line number. Learning to read the "stack trace" (the chain of function calls that led to the error) quickly narrows down where a bug lives.

Chapter 21

Objects

An object is a collection of key/value pairs, called properties. Objects are the primary way JavaScript models real-world entities.

const person = {
  name: "Ada Lovelace",
  age: 28,
  isProgrammer: true,
};

console.log(person.name);     // dot notation -> "Ada Lovelace"
console.log(person["age"]);   // bracket notation -> 28

Bracket notation is required when the property name is stored in a variable or isn't a valid identifier:

const key = "age";
console.log(person[key]); // 28

Adding, updating, and deleting properties

person.email = "ada@example.com"; // add
person.age = 29;                   // update
delete person.isProgrammer;        // delete

Nested objects

const user = {
  name: "Bo",
  address: {
    city: "Nairobi",
    country: "Kenya",
  },
};
console.log(user.address.city); // "Nairobi"

Checking for a property

"name" in person;              // true
person.hasOwnProperty("name"); // true
Chapter 22

Object Methods

A method is simply a function stored as an object property. Methods let objects define their own behavior.

const calculator = {
  value: 0,
  add(n) {
    this.value += n;
    return this;      // returning `this` allows chaining
  },
  subtract(n) {
    this.value -= n;
    return this;
  },
};

calculator.add(5).subtract(2);
console.log(calculator.value); // 3

Understanding this

Inside a regular method, this refers to the object the method was called on. This is dynamic — it depends on how the function is called, not where it was defined.

const dog = {
  name: "Rex",
  bark() {
    console.log(`${this.name} says woof!`);
  },
};
dog.bark(); // "Rex says woof!"

const bark = dog.bark;
bark(); // TypeError-ish: this.name is undefined, because `this` lost its context

Useful built-in Object methods

Object.keys(person);    // array of property names
Object.values(person);  // array of property values
Object.entries(person); // array of [key, value] pairs
Object.assign({}, person, { age: 30 }); // shallow-copy and merge
Object.freeze(person);  // prevent any further changes
Chapter 23

Object Destructuring

Destructuring lets you unpack values from objects (and arrays) into individual variables in a single, readable line.

const person = { name: "Ada", age: 28, city: "London" };

const { name, age } = person;
console.log(name, age); // "Ada" 28

Renaming while destructuring

const { name: fullName } = person;
console.log(fullName); // "Ada"

Default values

const { country = "Unknown" } = person;
console.log(country); // "Unknown" — property doesn't exist, so the default is used

Nested destructuring

const user = { name: "Bo", address: { city: "Nairobi" } };
const { address: { city } } = user;
console.log(city); // "Nairobi"

In function parameters

function printUser({ name, age }) {
  console.log(`${name} is ${age} years old`);
}
printUser(person);

Destructuring is used constantly in modern JavaScript, especially for extracting props in frameworks like React and for pulling specific fields out of API responses.

Chapter 24

Arrays

An array is an ordered list of values, stored under numeric indices starting at 0.

const fruits = ["apple", "banana", "cherry"];
console.log(fruits[0]);       // "apple"
console.log(fruits.length);   // 3
fruits[1] = "blueberry";      // update
fruits.push("date");          // add to the end
fruits.pop();                 // remove from the end

Arrays can hold any type, including mixed types

const mixed = [1, "two", true, { three: 3 }, [4, 5]];

Common array operations

fruits.unshift("apricot"); // add to the start
fruits.shift();            // remove from the start
fruits.indexOf("cherry");  // find position (-1 if not found)
fruits.includes("cherry"); // true/false
fruits.slice(1, 3);        // returns a new array, doesn't modify original
fruits.splice(1, 1, "x");  // remove/insert in place, modifies original

Multidimensional arrays

const grid = [
  [1, 2, 3],
  [4, 5, 6],
];
console.log(grid[1][2]); // 6
Teaching note: Emphasize the difference between methods that mutate the original array (push, pop, splice, sort, reverse) and methods that return a new array without changing the original (slice, map, filter, concat). This distinction causes many real-world bugs.
Chapter 25

Array Methods

Beyond basic manipulation, JavaScript arrays have a rich set of methods for transforming and querying data — central to writing clean, functional-style code.

map — transform every element

const numbers = [1, 2, 3, 4];
const doubled = numbers.map((n) => n * 2);
// [2, 4, 6, 8]

filter — keep elements that pass a test

const evens = numbers.filter((n) => n % 2 === 0);
// [2, 4]

reduce — combine all elements into a single value

const total = numbers.reduce((sum, n) => sum + n, 0);
// 10

forEach — run a function for each element (no return value)

numbers.forEach((n) => console.log(n));

find and findIndex

const users = [{ id: 1 }, { id: 2 }, { id: 3 }];
users.find((u) => u.id === 2);      // { id: 2 }
users.findIndex((u) => u.id === 2); // 1

some and every

numbers.some((n) => n > 3);  // true  (at least one matches)
numbers.every((n) => n > 0); // true  (all match)

sort

const nums = [10, 2, 33, 4];
nums.sort(); // [10, 2, 33, 4] -> WRONG! sorts as strings by default
nums.sort((a, b) => a - b); // [2, 4, 10, 33] -> correct numeric sort
Teaching note: The default sort() converting numbers to strings is one of the most common "gotcha" bugs students encounter. Always pass a compare function when sorting numbers.

Strings

A string is a sequence of characters used to represent text. Strings in JavaScript are immutable — once created, a string's characters cannot be changed; operations that seem to modify a string actually return a new one.

Creating strings

const single = 'Hello';
const double = "World";
const template = `${single}, ${double}!`; // template literal, supports interpolation

Template literals

Backtick strings support embedded expressions with ${} and multi-line text without escape characters:

const name = "Ada";
const age = 28;
console.log(`${name} is ${age} years old, so next year she'll be ${age + 1}.`);

Accessing characters and length

const word = "hello";

Escape characters

"She said \"hi\""; // escaping a double quote
"Line one\nLine two"; // \n = new line
Chapter 27

String Methods

Strings come with many built-in methods for searching, transforming, and slicing text.

const text = "  Hello, World!  ";

text.trim();              // "Hello, World!" (removes surrounding whitespace)
text.toUpperCase();       // "  HELLO, WORLD!  "
text.toLowerCase();       // "  hello, world!  "
text.includes("World");   // true
text.indexOf("World");    // position of first match
text.replace("World", "JS"); // replaces first match
text.replaceAll("l", "L");   // replaces every match
text.split(", ");            // ["  Hello", "World!  "]
text.slice(2, 7);            // extracts a substring by index
text.trim().padStart(20, "*"); // pad to a fixed width

Combining strings

"Hello".concat(", ", "World!"); // "Hello, World!"
"Hello" + ", " + "World!";       // same result, more common in practice

Checking start/end

"hello.js".startsWith("hello"); // true
"hello.js".endsWith(".js");     // true
Teaching note: Reinforce that none of these methods change the original string — they all return a new one. This connects back to string immutability from the previous chapter.
Chapter 28

Numbers

JavaScript has a single Number type for all numeric values (integers and floats alike), based on the IEEE 754 double-precision floating-point standard.

const integer = 42;
const float = 3.14;
const negative = -7;
const scientific = 5e3; // 5000

Common numeric pitfalls

0.1 + 0.2; // 0.30000000000000004 — floating point imprecision
Number.isInteger(5);   // true
Number.isInteger(5.5); // false
1 / 0;   // Infinity
-1 / 0;  // -Infinity
0 / 0;   // NaN ("Not a Number")
isNaN("abc" / 2); // true

Formatting numbers

(1234.5678).toFixed(2);       // "1234.57" (string, rounded to 2 decimals)
(255).toString(16);            // "ff" (convert to hexadecimal string)
(1234567).toLocaleString();   // "1,234,567" (locale-aware formatting)

BigInt for very large integers

const big = 9007199254740993n; // beyond Number.MAX_SAFE_INTEGER, use BigInt

Math Object

Math is a built-in object (not a function or constructor) that provides mathematical constants and functions.

Constants

Rounding

Math.round(4.5);  // 5
Math.floor(4.9);  // 4  (always rounds down)
Math.ceil(4.1);   // 5  (always rounds up)

Chapter 30

Date Object

The Date object represents a single moment in time and provides methods to read and manipulate dates and times.

Creating dates

const now = new Date();                     // current date and time
const specific = new Date("2026-07-28");    // from an ISO string
const detailed = new Date(2026, 6, 28, 14, 30); // year, month (0-indexed!), day, hour, minute

A common beginner mistake: months are zero-indexed, so January is 0 and December is 11.

Reading parts of a date

const d = new Date();
d.getFullYear();  // e.g. 2026
d.getMonth();     // 0-11
d.getDate();      // day of month, 1-31
d.getDay();       // day of week, 0 (Sunday) - 6 (Saturday)
d.getHours();     // 0-23
d.getMinutes();
d.getSeconds();

Formatting dates

d.toDateString();     // "Tue Jul 28 2026"
d.toISOString();      // "2026-07-28T14:30:00.000Z"
d.toLocaleDateString(); // locale-aware, e.g. "7/28/2026"

Comparing and calculating with dates

const start = new Date("2026-01-01");
const end = new Date("2026-07-28");
const msInDay = 1000 * 60 * 60 * 24;
const daysBetween = Math.round((end - start) / msInDay); // subtracting dates gives milliseconds

PART IV

Modern JavaScript (ES6+)

Chapter 31

let, const and var

ES6 (2015) introduced let and const to address long-standing problems with var. Modern JavaScript style guides recommend never using var in new code.

Key differences

  • Scope: var is function-scoped; let/const are block-scoped.
  • Hoisting behavior: var is initialized to undefined when hoisted; let/const sit in the Temporal Dead Zone until their line runs (see Chapter 15).
  • Redeclaration: var allows redeclaring the same variable in the same scope silently; let/const throw a SyntaxError.
  • Reassignment: var and let can be reassigned; const cannot.
var x = 1;
var x = 2; // fine, but confusing

let y = 1;
let y = 2; // SyntaxError: Identifier 'y' has already been declared

const z = 1;
z = 2; // TypeError: Assignment to constant variable.

Recommended practice

Default to const. Switch to let only when a variable genuinely needs to be reassigned (loop counters, accumulators, values that change based on user interaction). Avoid var entirely in new code — it exists today mainly for reading legacy codebases.

Chapter 32

Template Literals

Template literals, introduced in ES6, use backticks (`) instead of quotes and support embedded expressions and multi-line text without special escape characters.

String interpolation

const name = "Ada";
const age = 28;
const message = `${name} is ${age} years old.`;
console.log(message); // "Ada is 28 years old."

Any valid JavaScript expression can go inside ${}, including function calls and arithmetic:

`Next year, ${name} will be ${age + 1}.`
`Uppercase: ${name.toUpperCase()}`

Multi-line strings

const html = `
  <ul>
    <li>Item 1</li>
    <li>Item 2</li>
  </ul>
`;

Before template literals, multi-line strings required manual \n characters or string concatenation across lines — template literals make generating HTML fragments and formatted text far more readable.

Tagged templates (advanced)

function highlight(strings, ...values) {
  return strings.reduce((acc, str, i) => `${acc}${str}${values[i] ? `<b>${values[i]}</b>` : ""}`, "");
}
highlight`Hello, ${name}! You are ${age}.`;

A tagged template lets a function process the literal and its interpolated values before producing the final string — used by libraries like styled-components.

Chapter 33

Arrow Functions

Arrow functions, introduced in ES6, offer a more concise syntax for writing functions and behave differently from regular functions in one crucial way: they do not bind their own this.

Syntax variations

const add = (a, b) => a + b;       // implicit return, no braces needed
const square = (n) => n * n;
const greet = name => `Hi ${name}`; // single parameter, parens optional
const noop = () => {};               // no parameters, empty braces required
const build = (a, b) => {            // explicit return with a block body
  const result = a + b;
  return result;
};

The this difference

Regular functions get their own this, determined by how they are called. Arrow functions inherit this from the surrounding (lexical) scope — they have no this of their own.

const timer = {
  seconds: 0,
  start() {
    setInterval(() => {
      this.seconds++;             // `this` correctly refers to `timer`
      console.log(this.seconds);
    }, 1000);
  },
};
timer.start();

If a regular function were used instead of the arrow function inside setInterval, this would not refer to timer, and this.seconds would be undefined. This makes arrow functions the natural choice for callbacks nested inside methods.

When not to use arrow functions

  • Object methods that need their own this — use a regular method shorthand instead (see Chapter 22).
  • Functions used as constructors — arrow functions cannot be used with new.
Chapter 34

Spread Operator

The spread operator (...) expands an iterable (array, string) or an object's own properties into individual elements. It is one of the most-used ES6+ features for writing concise, immutable-style code.

Spreading arrays

const nums = [1, 2, 3];
const more = [...nums, 4, 5];      // [1, 2, 3, 4, 5]
const copy = [...nums];             // a shallow copy, not a reference
const combined = [...nums, ...more]; // merge two arrays

Spreading objects

const person = { name: "Ada", age: 28 };
const updated = { ...person, age: 29 };       // { name: "Ada", age: 29 }
const withEmail = { ...person, email: "a@x.com" };

Spreading an object performs a shallow copy: nested objects are still shared by reference between the original and the copy.

Spreading into function calls

function sum(a, b, c) { return a + b + c; }
const args = [1, 2, 3];
sum(...args); // 6, same as sum(1, 2, 3)

Math.max(...[4, 9, 2]); // 9

Spreading strings

[..."hello"]; // ["h", "e", "l", "l", "o"]
Teaching note: Connect this directly to the immutability habits from Chapter 21 — spreading is the idiomatic way to update state without mutation, especially important once students reach frameworks like React.
Chapter 35

Rest Parameters

Rest parameters use the same ... syntax as spread, but in the opposite direction: instead of expanding values, they collect multiple arguments into a single array.

function sum(...numbers) {
  return numbers.reduce((total, n) => total + n, 0);
}
sum(1, 2, 3, 4); // 10 -- numbers is [1, 2, 3, 4]

Rest parameters alongside named parameters

function introduce(firstName, lastName, ...hobbies) {
  console.log(`${firstName} ${lastName} enjoys: ${hobbies.join(", ")}`);
}
introduce("Ada", "Lovelace", "math", "writing", "music");
// "Ada Lovelace enjoys: math, writing, music"

The rest parameter must be the last parameter in the function signature — JavaScript needs to know where the named parameters end and the rest begins.

Rest in destructuring

const [first, ...rest] = [1, 2, 3, 4];
console.log(first, rest); // 1 [2, 3, 4]

const { name, ...otherFields } = { name: "Ada", age: 28, city: "London" };
console.log(otherFields); // { age: 28, city: "London" }

Rest vs. the old arguments object

Before rest parameters, functions used the built-in arguments object to access extra arguments — but arguments is not a real array (no map, filter, etc.) and doesn't exist in arrow functions. Rest parameters are the modern, cleaner replacement.

Chapter 36

Destructuring

Chapter 23 introduced object destructuring. Destructuring also works on arrays, and the two forms are used constantly together in modern JavaScript to pull data out of complex structures cleanly.

Array destructuring

const colors = ["red", "green", "blue"];
const [first, second] = colors;
console.log(first, second); // "red" "green"

Skipping elements

const [, , third] = colors;
console.log(third); // "blue"

Swapping variables

let a = 1, b = 2;
[a, b] = [b, a];
console.log(a, b); // 2 1

Default values

const [x = 10, y = 20] = [5];
console.log(x, y); // 5 20

Destructuring function return values

function getCoordinates() {
  return [10, 20];
}
const [lat, lng] = getCoordinates();

function getUser() {
  return { name: "Ada", age: 28 };
}
const { name, age } = getUser();

Combined with rest parameters, destructuring is the standard way modern JavaScript unpacks API responses, component props, and configuration objects.

Chapter 37

Modules

Modules let you split code across multiple files, each with its own scope, and explicitly control what is shared between them using export and import. This replaces older patterns of loading many separate <script> tags that all shared one global scope.

Named exports

// math.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;

// main.js
import { add, PI } from "./math.js";
console.log(add(2, 3), PI);

Default exports

// user.js
export default function createUser(name) {
  return { name };
}

// main.js
import createUser from "./user.js"; // no curly braces for a default import

Renaming and namespace imports

import { add as sum } from "./math.js";
import * as MathUtils from "./math.js";
MathUtils.add(2, 3);

Using modules in the browser

<script type="module" src="main.js"></script>

Modules loaded with type="module" are deferred automatically, run in strict mode by default, and have their own scope — variables declared in one module don't leak into another.

Modules in Node.js

Node supports this same ES module syntax (with a "type": "module" setting in package.json) as well as its older CommonJS system (require/module.exports), which is still common in existing codebases.

Chapter 38

Classes

Classes, introduced in ES6, provide cleaner syntax for creating objects that share the same structure and behavior. Under the hood, they still use JavaScript's existing prototype system — a class is often described as "syntactic sugar" over it.

Defining a class

class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }
  greet() {
    console.log(`Hi, I'm ${this.name}`);
  }
}

const ada = new Person("Ada", 28);
ada.greet(); // "Hi, I'm Ada"

The constructor

The constructor method runs automatically when a new instance is created with new. It's where you set up the object's initial properties.

Static methods and properties

class MathHelper {
  static square(n) {
    return n * n;
  }
}
MathHelper.square(4); // 16 -- called on the class itself, not an instance

Getters and setters

class Circle {
  constructor(radius) {
    this.radius = radius;
  }
  get area() {
    return Math.PI * this.radius ** 2;
  }
}
const c = new Circle(5);
console.log(c.area); // accessed like a property, not called like a method
Teaching note: Emphasize that classes are not a separate type system layered on top of JavaScript — every class instance is still a plain object underneath, and typeof ada is "object".
Chapter 39

Inheritance

Inheritance lets one class build on another, reusing and extending its behavior. JavaScript classes use the extends and super keywords for this.

class Animal {
  constructor(name) {
    this.name = name;
  }
  speak() {
    console.log(`${this.name} makes a sound.`);
  }
}

class Dog extends Animal {
  speak() {
    super.speak();                       // call the parent's version too
    console.log(`${this.name} barks.`);
  }
}

const rex = new Dog("Rex");
rex.speak();
// "Rex makes a sound."
// "Rex barks."

super in the constructor

When a subclass defines its own constructor, it must call super(...) before using this — this runs the parent class's constructor first.

class Cat extends Animal {
  constructor(name, indoor) {
    super(name);        // must run first
    this.indoor = indoor;
  }
}

instanceof

rex instanceof Dog;    // true
rex instanceof Animal; // true -- Dog inherits from Animal

Why use inheritance

Inheritance is useful when several classes genuinely share behavior and a clear "is-a" relationship (a Dog is an Animal). When the relationship is looser, composition (building objects out of smaller, reusable pieces) is often a more flexible alternative.

Chapter 40

Private Fields

Private class fields, a more recent addition to JavaScript, let a class hide internal data so it cannot be accessed or modified from outside the class. They are written with a # prefix.

class BankAccount {
  #balance = 0; // private field

  constructor(owner) {
    this.owner = owner;
  }

  deposit(amount) {
    this.#balance += amount;
  }

  get balance() {
    return this.#balance;
  }
}

const account = new BankAccount("Ada");
account.deposit(100);
console.log(account.balance); // 100 -- accessed through a public getter
console.log(account.#balance); // SyntaxError: Private field '#balance' must be declared in an enclosing class

Private methods

class Validator {
  #isPositive(n) {
    return n > 0;
  }
  check(n) {
    return this.#isPositive(n) ? "valid" : "invalid";
  }
}

Why private fields matter

Before private fields, JavaScript developers simulated privacy with closures (see Chapter 16) or a naming convention like _balance — but a leading underscore was only a signal, not real enforcement; the property was still fully accessible. True private fields (#balance) are enforced by the language itself: any access from outside the class throws an error, not just a warning.

PART V

DOM Manipulation

Chapter 41

Understanding the DOM

The DOM (Document Object Model) is the browser's live, in-memory representation of an HTML page. It models the page as a tree of nodes — elements, text, and attributes — that JavaScript can read and modify, causing the page to update instantly.

The document tree

<html>
  <body>
    <h1>Title</h1>
    <p>Some text</p>
  </body>
</html>

The browser turns this into a tree: html is the root, with a body child, which has h1 and p children. Every tag becomes an element node, and the text inside becomes a text node.

document as the entry point

JavaScript accesses this tree through the global document object, which represents the entire page.

console.log(document.title);      // the page's 
console.log(document.body);       // the <body> element node</body>

Why the DOM matters

HTML and CSS describe what a page looks like when it first loads. The DOM is what lets JavaScript change that page after it has loaded — adding a to-do item, showing a validation message, updating a shopping cart total — all without a full page reload.

Teaching note: A good first exercise: open DevTools' Elements panel, edit some text directly in the browser, and discuss how that's exactly what JavaScript DOM methods do programmatically.
Chapter 42

Selecting Elements

Before you can change a page with JavaScript, you need to select the element(s) you want to work with.

Selecting a single element

document.getElementById("main-title");
document.querySelector(".card");        // first match of any CSS selector
document.querySelector("#main-title");
document.querySelector("ul li:first-child");

Selecting multiple elements

document.getElementsByClassName("card");  // live HTMLCollection
document.getElementsByTagName("li");       // live HTMLCollection
document.querySelectorAll(".card");        // static NodeList

querySelector and querySelectorAll are the most flexible: they accept any valid CSS selector, so anything you can select in a stylesheet, you can select in JavaScript.

Live collections vs. static NodeLists

getElementsByClassName/getElementsByTagName return "live" collections that automatically update if the DOM changes; querySelectorAll returns a static snapshot taken at the moment it's called.

Looping over a NodeList

const cards = document.querySelectorAll(".card");
cards.forEach((card) => console.log(card));
Teaching note: Recommend querySelector/querySelectorAll as the default for beginners — the CSS selector syntax is already familiar from Level 2 (CSS), and it avoids the live-collection gotchas of the older methods.
Chapter 43

Changing HTML

Once an element is selected, JavaScript can read or replace its content.

textContent vs. innerText vs. innerHTML

const el = document.querySelector("#message");

el.textContent = "Hello, world!";        // sets plain text, fast, safe
el.innerHTML = "<strong>Hello!</strong>"; // parses and renders HTML tags
console.log(el.textContent);              // reads the text content back
  • textContent — gets/sets raw text; any HTML tags are shown literally, not rendered. Fast and safe against injection.
  • innerHTML — gets/sets content as HTML, parsing tags into real elements. Powerful, but inserting untrusted user input this way is a security risk (cross-site scripting).
  • innerText — similar to textContent, but respects CSS styling (e.g. ignores hidden elements) and is slower because it triggers layout calculations.

Working with attributes

const link = document.querySelector("a");
link.getAttribute("href");
link.setAttribute("href", "https://example.com");
link.removeAttribute("target");
link.hasAttribute("href"); // true
Teaching note: Introduce the security note early: never insert raw, un-sanitized user input with innerHTML. Use textContent when displaying anything a user typed.
Chapter 44

Changing CSS

JavaScript can read and change an element's styling in two main ways: directly through the style property, or by toggling CSS classes.

Inline styles via the style property

const box = document.querySelector(".box");
box.style.backgroundColor = "tomato";
box.style.width = "200px";
box.style.display = "none";

CSS properties with hyphens (like background-color) become camelCase in JavaScript (backgroundColor).

Toggling classes (the preferred approach)

box.classList.add("active");
box.classList.remove("active");
box.classList.toggle("active");    // adds if absent, removes if present
box.classList.contains("active");  // true/false

Toggling a class defined in your stylesheet keeps styling logic in CSS and JavaScript logic in JavaScript — generally cleaner and easier to maintain than setting many individual inline style properties.

Reading computed styles

const styles = getComputedStyle(box);
console.log(styles.color); // the actual rendered color, including inherited/CSS rules
Chapter 45

Creating Elements

JavaScript can build entirely new elements and insert them into the page — the foundation of dynamic UIs like to-do lists, comment sections, and search results.

Creating and configuring an element

const li = document.createElement("li");
li.textContent = "New item";
li.classList.add("list-item");

Inserting it into the page

const list = document.querySelector("ul");
list.appendChild(li);          // adds as the last child
list.prepend(li);              // adds as the first child
list.insertBefore(li, list.firstChild); // insert before a specific reference node

Modern insertion methods

list.append(li, "some text");     // can insert multiple nodes/strings at once
existingItem.before(li);           // insert li just before existingItem
existingItem.after(li);            // insert li just after existingItem

Building a small list from data

const fruits = ["apple", "banana", "cherry"];
const ul = document.querySelector("#fruit-list");

fruits.forEach((fruit) => {
  const item = document.createElement("li");
  item.textContent = fruit;
  ul.appendChild(item);
});
Teaching note: This chapter pairs naturally with Chapter 25 (Array Methods) — using .map() or .forEach() to turn an array of data into DOM elements is one of the most common real-world patterns.
Chapter 46

Removing Elements

Just as elements can be created and inserted, they can be removed from the page when no longer needed.

The modern way: remove()

const item = document.querySelector(".item");
item.remove(); // removes the element from the DOM entirely

The older way: removeChild()

const list = document.querySelector("ul");
const item = document.querySelector(".item");
list.removeChild(item); // requires a reference to the parent

remove() is simpler because it doesn't require a reference to the parent element, but removeChild() is still common in older code and some cross-browser-compatible libraries.

Clearing all children of an element

const container = document.querySelector("#container");
container.innerHTML = ""; // quick, but re-parses; fine for small amounts of content

// A more explicit alternative:
while (container.firstChild) {
  container.removeChild(container.firstChild);
}

Removing based on a condition

document.querySelectorAll(".item").forEach((item) => {
  if (item.dataset.completed === "true") {
    item.remove();
  }
});
Chapter 47

DOM Traversing

Traversing means moving between related elements in the DOM tree — from a child to its parent, between siblings, and so on — without needing a new selector query each time.

Parent, children, and siblings

const item = document.querySelector(".item");

item.parentElement;        // the element's direct parent
item.children;              // an HTMLCollection of direct child elements
item.firstElementChild;
item.lastElementChild;
item.nextElementSibling;    // the next element at the same level
item.previousElementSibling;

Element vs. Node traversal properties

Properties ending in Element (like nextElementSibling) skip text and comment nodes, returning only actual elements — almost always what you want. The plain versions (nextSibling, childNodes) include text nodes too, which often represent whitespace between tags.

Practical example: finding a related element

document.querySelectorAll(".delete-btn").forEach((btn) => {
  btn.addEventListener("click", () => {
    const listItem = btn.closest("li"); // walks up to the nearest 
  •  ancestor
    listItem.remove();
  });
});

    • closest() is especially useful: it searches upward from an element through its ancestors until it finds one matching a given CSS selector, or returns null if none match.

    Chapter 48

    Forms

    Forms are how users submit data on the web, and JavaScript can read, validate, and react to form input in real time.

    Accessing form values

    <form id="signup">
  <input type="text" name="username">
  <input type="email" name="email">
  <button type="submit">Sign up</button>
</form>

const form = document.querySelector("#signup");
const username = form.elements["username"].value;

    Handling submission

    form.addEventListener("submit", (event) => {
  event.preventDefault(); // stop the default full-page reload/navigation
  const data = new FormData(form);
  console.log(data.get("username"), data.get("email"));
});

    event.preventDefault() is essential in modern form handling: without it, the browser performs its default action (submitting to a URL and reloading the page), interrupting any JavaScript-driven behavior.

    Reading values as the user types

    const emailInput = document.querySelector("input[name='email']");
emailInput.addEventListener("input", (event) => {
  console.log(event.target.value);
});

    The FormData object

    FormData automatically collects every named field in a form, making it easy to send the whole form's data to a server without reading each field manually one at a time.

    Chapter 49

    Validation

    Validation ensures the data a user submits meets expected rules before it's processed — a required field isn't empty, an email looks like an email, a password is long enough.

    Built-in HTML validation

    <input type="email" required>
<input type="text" minlength="3" maxlength="20" required>
<input type="number" min="1" max="100">

    Attributes like required, minlength, and type="email" give the browser free, built-in validation with no JavaScript at all, including automatic error messages.

    Custom JavaScript validation

    form.addEventListener("submit", (event) => {
  const username = form.elements["username"].value.trim();
  const errors = [];

  if (username.length < 3) {
    errors.push("Username must be at least 3 characters.");
  }
  if (!form.elements["email"].value.includes("@")) {
    errors.push("Please enter a valid email address.");
  }

  if (errors.length > 0) {
    event.preventDefault();
    console.log(errors.join(" "));
  }
});

    The Constraint Validation API

    const input = form.elements["email"];
input.checkValidity();          // true/false, based on the built-in rules
input.setCustomValidity("");    // clear a custom error
input.setCustomValidity("Please use your company email."); // set a custom error message
    Teaching note: Emphasize that client-side validation is for user experience only — it can always be bypassed, so the same rules must also be enforced on the server. This connects naturally to Part VII's discussion of APIs.
    Chapter 50

    Event Handling

    Events are how a page responds to things happening — a click, a key press, a page load, a form submission. Event handling is what makes a page interactive.

    Adding an event listener

    const button = document.querySelector("#submit-btn");
button.addEventListener("click", () => {
  console.log("Button clicked!");
});

    The event object

    button.addEventListener("click", (event) => {
  console.log(event.target);   // the element that triggered the event
  console.log(event.type);     // "click"
});

    Common event types

    • Mouse: click, dblclick, mouseover, mouseout
    • Keyboard: keydown, keyup, keypress
    • Form: submit, input, change, focus, blur
    • Document/window: DOMContentLoaded, load, resize, scroll

    Event bubbling and delegation

    Events "bubble" upward from the target element through its ancestors. This lets you attach a single listener to a parent element to handle events from many children — called event delegation, especially useful for elements added dynamically after the page loads.

    document.querySelector("ul").addEventListener("click", (event) => {
  if (event.target.tagName === "LI") {
    event.target.classList.toggle("done");
  }
});

    Removing a listener

    function handleClick() { console.log("clicked"); }
button.addEventListener("click", handleClick);
button.removeEventListener("click", handleClick); // must pass the same function reference

    Chapter 51

    Window Object

    The window object represents the browser tab or window itself and sits at the very top of the browser's object hierarchy. Every global variable and function (including document) is actually a property of window.

    console.log(window.innerWidth);   // viewport width in pixels
console.log(window.innerHeight);  // viewport height in pixels
window.alert("Hello!");           // shows a browser alert dialog
window.confirm("Are you sure?");  // shows OK/Cancel, returns true/false
window.prompt("Your name?");      // shows a text input dialog, returns the string or null

    Timers live on window

    window.setTimeout(() => console.log("later"), 1000);
window.setInterval(() => console.log("repeating"), 1000);

    Because these are properties of the global window object, you can (and usually do) call them without the window. prefix — setTimeout(...) works the same as window.setTimeout(...).

    Opening and resizing windows

    window.open("https://example.com", "_blank");
window.close(); // only works on windows opened by script
window.resizeTo(800, 600);

    Listening for window-level events

window.addEventListener("load", () => console.log("everything finished loading"));

    Document Object

    document represents the loaded web page itself and is the main entry point for everything covered in Part V (DOM Manipulation). It is a property of window, but used so often it's treated as its own top-level object.

    Useful document properties

document.URL;            // the full current URL as a string
document.domain;         // the domain name
document.characterSet;   // e.g. "UTF-8"

    Chapter 54

    Screen Object

    screen provides information about the user's physical display — useful for responsive behavior that depends on hardware rather than just the browser window.

    screen.width;        // full screen width in pixels
screen.height;        // full screen height in pixels
screen.availWidth;    // width available, excluding OS elements like the taskbar
screen.availHeight;
screen.colorDepth;    // bits per pixel, typically 24 or 30
screen.orientation.type; // e.g. "landscape-primary"

    screen vs. window dimensions

    It's easy to confuse screen with window: screen.width is the size of the entire monitor, while window.innerWidth is the size of the visible browser viewport — the number that matters for most responsive-design decisions in JavaScript.

    Reacting to orientation changes

    screen.orientation.addEventListener("change", () => {
  console.log("New orientation:", screen.orientation.type);
});

    In practice, most responsive behavior should be handled with CSS media queries; the screen object is reserved for JavaScript logic that specifically needs to know about the physical display, such as games or drawing applications.

    Chapter 55

    Location Object

    location (accessible as window.location or document.location) represents the current URL and provides methods to navigate to a new one.

    Reading URL parts

    // For https://example.com:8080/products?id=42#reviews
location.href;      // "https://example.com:8080/products?id=42#reviews" -- the full URL
location.protocol;  // "https:"
location.host;      // "example.com:8080"
location.hostname;  // "example.com"
location.pathname;  // "/products"
location.search;    // "?id=42"
location.hash;       // "#reviews"

    Reading query parameters properly

    const params = new URLSearchParams(location.search);
params.get("id"); // "42"

    Navigating with JavaScript

    location.href = "https://example.com/login"; // navigate to a new page
location.assign("https://example.com");        // same effect as setting href
location.replace("https://example.com");       // navigates without adding a history entry
location.reload();                               // reload the current page

    The difference between assign and replace matters for the back button: replace swaps out the current history entry, so the user can't navigate "back" to the page they came from — useful after a login redirect.

    Chapter 56

    History Object

    history gives JavaScript control over the browser's session history — the stack of pages a user has visited in the current tab.

    history.length;     // number of entries in the session history
history.back();     // equivalent to clicking the browser's back button
history.forward();  // equivalent to clicking forward
history.go(-2);      // go back two entries; history.go(1) goes forward one

    Changing the URL without a full reload

    history.pushState({ page: 2 }, "", "/products?page=2");
history.replaceState({ page: 2 }, "", "/products?page=2");

    pushState adds a new entry to the history and updates the visible URL, without the browser actually loading a new page — this is the foundation of "single-page applications" (SPAs), where navigation feels instant because only page content is swapped via JavaScript.

    Reacting to back/forward navigation

    window.addEventListener("popstate", (event) => {
  console.log("Navigated via back/forward, state:", event.state);
});
    Teaching note: This chapter is a good bridge to explaining what frameworks like React Router or Vue Router are actually doing under the hood — they wrap these exact native browser APIs.
    Chapter 57

    Local Storage

    localStorage lets a website store key/value data directly in the browser, persisting even after the tab or browser is closed, until explicitly cleared.

    Basic usage

    localStorage.setItem("username", "ada");
localStorage.getItem("username");   // "ada"
localStorage.removeItem("username");
localStorage.clear();                // removes everything stored by this site

    Storing objects and arrays

    localStorage only stores strings, so objects and arrays must be converted with JSON.stringify and parsed back with JSON.parse (see Chapter 65).

    const user = { name: "Ada", age: 28 };
localStorage.setItem("user", JSON.stringify(user));

const stored = JSON.parse(localStorage.getItem("user"));
console.log(stored.name); // "Ada"

    Characteristics

    • Persists indefinitely, across browser restarts, until manually cleared.
    • Scoped per-origin (protocol + domain + port) — one site cannot read another's storage.
    • Storage limit is roughly 5–10MB depending on the browser.
    • Synchronous, so avoid storing very large amounts of data that could block the main thread.
    Teaching note: Never store sensitive data (passwords, tokens meant to stay private) in localStorage — it's readable by any JavaScript running on the page, making it a target if the site has a cross-site scripting vulnerability.
    Chapter 58

    Session Storage

    sessionStorage has the exact same API as localStorage, with one key difference: data only persists for the lifetime of the current browser tab.

    sessionStorage.setItem("step", "2");
sessionStorage.getItem("step");   // "2"
sessionStorage.removeItem("step");
sessionStorage.clear();

    localStorage vs. sessionStorage

    • localStorage — persists across tabs, windows, and browser restarts, until cleared explicitly.
    • sessionStorage — cleared automatically when the tab is closed; not shared between tabs, even for the same site.

    When to use sessionStorage

    sessionStorage is a good fit for temporary state that shouldn't outlive the current visit — the current step of a multi-page form, a temporary filter selection, or a "don't show this again" flag that should reset next time the user returns.

    // Multi-step form example
sessionStorage.setItem("formStep", "2");
sessionStorage.setItem("formData", JSON.stringify({ name: "Ada" }));
    Chapter 59

    Cookies

    Cookies are small pieces of data stored in the browser and automatically sent to the server with every HTTP request to the same domain — unlike localStorage/sessionStorage, which stay entirely on the client unless JavaScript sends them somewhere.

    Reading and writing cookies with JavaScript

    document.cookie = "username=ada; max-age=3600; path=/";
console.log(document.cookie); // "username=ada" (and any other cookies, semicolon-separated)

    document.cookie is a single string containing all cookies for the page, which makes reading a specific cookie's value manually a bit awkward — most projects use a small helper function or a library to parse it.

    Common cookie attributes

    • max-age / expires — how long the cookie should live before it's automatically deleted.
    • path — which URL paths the cookie applies to.
    • secure — only sent over HTTPS connections.
    • HttpOnly — only settable by the server, not readable by JavaScript at all (a common security measure for session tokens).
    • SameSite — controls whether the cookie is sent with cross-site requests, an important defense against certain attacks.

    Cookies vs. Web Storage

    Cookies are automatically included in every request to the server (useful for authentication), but are limited to about 4KB and add overhead to every request. localStorage/sessionStorage are larger and stay client-side only, making them better suited for data the server never needs to see.

    Chapter 60

    Clipboard API

    The Clipboard API lets JavaScript read from and write to the system clipboard — the mechanism behind copy/paste. It replaces older, less reliable approaches like document.execCommand("copy").

    Copying text to the clipboard

    async function copyText(text) {
  try {
    await navigator.clipboard.writeText(text);
    console.log("Copied!");
  } catch (error) {
    console.error("Copy failed:", error);
  }
}

document.querySelector("#copy-btn").addEventListener("click", () => {
  copyText("Hello, clipboard!");
});

    Reading from the clipboard

    async function pasteText() {
  const text = await navigator.clipboard.readText();
  console.log("Clipboard contains:", text);
}

    Security considerations

    • The Clipboard API requires a secure context (HTTPS, or localhost during development).
    • Reading the clipboard typically requires explicit user permission or a direct user gesture (like a button click) — a page cannot silently read clipboard contents in the background.

    A common real-world pattern: "Copy link" button

    document.querySelector("#copy-link").addEventListener("click", async (event) => {
  await navigator.clipboard.writeText(location.href);
  event.target.textContent = "Copied!";
  setTimeout(() => { event.target.textContent = "Copy link"; }, 2000);
});
    PART VII

    Asynchronous JavaScript

    Chapter 61

    Callbacks

    A callback is simply a function passed as an argument to another function, to be "called back" later — often once some asynchronous operation completes. Callbacks were JavaScript's original way of handling asynchronous code, before Promises existed.

    A basic callback

    function processData(data, callback) {
  const result = data.toUpperCase();
  callback(result);
}
processData("hello", (result) => console.log(result)); // "HELLO"

    Asynchronous callbacks

    console.log("Start");
setTimeout(() => {
  console.log("This runs later");
}, 1000);
console.log("End");
// Logs: "Start", "End", then "This runs later" after 1 second

    Callback hell

    When many asynchronous steps depend on each other, callbacks nested inside callbacks quickly become hard to read — a pattern nicknamed "callback hell" or the "pyramid of doom":

    getUser(id, (user) => {
  getPosts(user, (posts) => {
    getComments(posts[0], (comments) => {
      console.log(comments); // deeply nested, hard to follow or handle errors
    });
  });
});

    This exact problem is what Promises (Chapter 62) and async/await (Chapter 63) were designed to solve, and understanding callbacks first makes clear exactly what problem they're solving.

    Chapter 62

    Promises

    A Promise is an object representing the eventual result of an asynchronous operation. It exists in one of three states: pending (not yet finished), fulfilled (completed successfully), or rejected (failed).

    Creating a Promise

    const promise = new Promise((resolve, reject) => {
  const success = true;
  setTimeout(() => {
    if (success) {
      resolve("Data loaded!");
    } else {
      reject(new Error("Failed to load"));
    }
  }, 1000);
});

    Consuming a Promise

    promise
  .then((result) => console.log(result))
  .catch((error) => console.error(error.message))
  .finally(() => console.log("Done, either way"));

    Chaining promises

    Each .then() returns a new Promise, allowing sequential asynchronous steps without nesting:

    getUser(id)
  .then((user) => getPosts(user))
  .then((posts) => getComments(posts[0]))
  .then((comments) => console.log(comments))
  .catch((error) => console.error("Something failed:", error.message));

    Compare this to the nested callback example in Chapter 61 — the same logic, but flat and readable, with a single .catch() handling errors from any step in the chain.

    Running promises in parallel

    Promise.all([fetchA(), fetchB(), fetchC()])
  .then(([resultA, resultB, resultC]) => console.log(resultA, resultB, resultC));

Promise.race([fetchA(), fetchB()]); // resolves/rejects as soon as the first one settles
Promise.allSettled([fetchA(), fetchB()]); // waits for all, regardless of success/failure
    Chapter 63

    Async/Await

    async/await, introduced in ES2017, is syntax built on top of Promises that lets asynchronous code be written and read almost like ordinary synchronous code.

    Declaring an async function

    async function loadData() {
  return "Data loaded!"; // automatically wrapped in a resolved Promise
}
loadData().then((result) => console.log(result));

    Any function marked async always returns a Promise, even if you just return a plain value.

    Using await

    async function getUserData(id) {
  const user = await getUser(id);       // pauses here until the Promise resolves
  const posts = await getPosts(user);
  const comments = await getComments(posts[0]);
  return comments;
}

    Compare this directly to the Promise-chain version from Chapter 62: the logic is identical, but await lets it read top-to-bottom like synchronous code, without .then() chains.

    Error handling with try/catch

    async function getUserData(id) {
  try {
    const user = await getUser(id);
    const posts = await getPosts(user);
    return posts;
  } catch (error) {
    console.error("Failed to load user data:", error.message);
  }
}

    await only works inside async functions (mostly)

    await can only be used inside a function declared async — except at the top level of a module, where "top-level await" is allowed directly.

    Teaching note: Teach Promises first, then async/await as "the same thing, easier to read" — students who skip straight to async/await often struggle later when they need Promise.all() for parallel operations, since async/await alone only expresses sequential steps.
    Chapter 64

    Fetch API

    The Fetch API is the modern, built-in way to make HTTP requests from JavaScript — retrieving data from a server, submitting form data, or calling a REST API, all covered further in Chapters 66 and 67.

    A basic GET request

    fetch("https://api.example.com/users")
  .then((response) => response.json())  // parses the response body as JSON
  .then((data) => console.log(data))
  .catch((error) => console.error("Request failed:", error.message));

    Using fetch with async/await

    async function getUsers() {
  try {
    const response = await fetch("https://api.example.com/users");
    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }
    const data = await response.json();
    return data;
  } catch (error) {
    console.error(error.message);
  }
}

    An important detail: fetch only rejects on a network failure, not on HTTP error statuses like 404 or 500. Checking response.ok (true for status 200–299) is necessary to catch server-side errors.

    Sending data with POST

    fetch("https://api.example.com/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Ada", age: 28 }),
})
  .then((response) => response.json())
  .then((data) => console.log("Created:", data));
    Chapter 65

    JSON

    JSON (JavaScript Object Notation) is a lightweight, text-based data format used to exchange data between a browser and a server — and, despite the name, is used by virtually every programming language, not just JavaScript.

    JSON syntax rules

    {
  "name": "Ada",
  "age": 28,
  "isProgrammer": true,
  "hobbies": ["math", "writing"],
  "address": { "city": "London" }
}

    JSON keys must always be double-quoted strings, values can be strings, numbers, booleans, null, arrays, or nested objects — but never functions, undefined, or JavaScript-specific types.

    Converting between JSON and JavaScript objects

    const user = { name: "Ada", age: 28 };

const jsonString = JSON.stringify(user);
// '{"name":"Ada","age":28}' -- a string, ready to send over a network or store

const parsedBack = JSON.parse(jsonString);
// { name: "Ada", age: 28 } -- a real JavaScript object again

    Pretty-printing JSON

    JSON.stringify(user, null, 2); // adds 2-space indentation for readability

    Where JSON shows up

    • Request and response bodies in fetch calls (Chapters 64, 66, 67).
    • Storing structured data in localStorage/sessionStorage (Chapters 57, 58).
    • Configuration files, like package.json in Node.js projects.
    Chapter 66

    REST APIs

    REST (Representational State Transfer) is a widely used architectural style for designing web APIs — a set of conventions for how a client (like a browser) and a server communicate over HTTP.

    Core REST concepts

    • Resources — everything is modeled as a resource with a URL, e.g. /users, /users/42.
    • HTTP methods map to actions: GET (read), POST (create), PUT/PATCH (update), DELETE (remove).
    • Status codes communicate the result: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 500 Server Error.

    Example: a full CRUD interaction

    // Read all users
fetch("/api/users");

// Create a user
fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Ada" }),
});

// Update a user
fetch("/api/users/42", {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ age: 29 }),
});

// Delete a user
fetch("/api/users/42", { method: "DELETE" });

    Authentication

    Many REST APIs require an authentication token, usually sent in a request header:

    fetch("/api/profile", {
  headers: { Authorization: `Bearer ${token}` },
});
    Chapter 67

    AJAX

    AJAX (Asynchronous JavaScript and XML) is the general technique of a web page communicating with a server in the background, updating parts of the page without a full reload — the concept that made modern, dynamic web apps possible, well before the word "XML" stopped being accurate (most AJAX today exchanges JSON, not XML).

    The original tool: XMLHttpRequest

    const xhr = new XMLHttpRequest();
xhr.open("GET", "https://api.example.com/users");
xhr.onload = function () {
  if (xhr.status === 200) {
    const data = JSON.parse(xhr.responseText);
    console.log(data);
  }
};
xhr.onerror = function () {
  console.error("Request failed");
};
xhr.send();

    Why fetch replaced XMLHttpRequest

    XMLHttpRequest is callback-based and verbose. The Fetch API (Chapter 64) achieves the same "AJAX" goal — requesting data without a page reload — with a cleaner, Promise-based interface that works naturally with async/await.

    // The same request, using fetch instead
async function getUsers() {
  const response = await fetch("https://api.example.com/users");
  return response.json();
}
    Teaching note: "AJAX" today refers to the general pattern (asynchronous background requests), not a specific API. Students will still encounter XMLHttpRequest in older tutorials and codebases, so recognizing it is useful even though fetch is the modern default.
    Chapter 68

    Error Handling in Async Code

    Errors in asynchronous code need special handling, because a regular try...catch around a callback-based async call won't actually catch errors that happen later, after the surrounding code has already finished running.

    Errors with Promises

    fetch("/api/users")
  .then((response) => {
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  })
  .catch((error) => {
    console.error("Request failed:", error.message);
  });

    Errors with async/await

    async function getUsers() {
  try {
    const response = await fetch("/api/users");
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return await response.json();
  } catch (error) {
    console.error("Request failed:", error.message);
    return null; // a sensible fallback value
  }
}

    A common mistake

    try {
  setTimeout(() => {
    throw new Error("This will NOT be caught!");
  }, 1000);
} catch (error) {
  console.log("This never runs");
}

    The try...catch block finishes executing before the setTimeout callback ever runs, so it cannot catch an error thrown inside it. The error handling must live inside the asynchronous callback, or use Promises/async-await, which are specifically designed to propagate errors correctly across asynchronous boundaries.

    Unhandled rejections

    window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled Promise rejection:", event.reason);
});
    Chapter 69

    Timers

    JavaScript provides two main functions for scheduling code to run after a delay or repeatedly: setTimeout and setInterval.

    setTimeout — run once, after a delay

    const timerId = setTimeout(() => {
  console.log("Runs once, after 2 seconds");
}, 2000);

clearTimeout(timerId); // cancels it, if called before the delay elapses

    setInterval — run repeatedly

    const intervalId = setInterval(() => {
  console.log("Runs every 1 second");
}, 1000);

clearInterval(intervalId); // stops the repetition

    A common pattern: a countdown

    let secondsLeft = 5;
const countdown = setInterval(() => {
  console.log(secondsLeft);
  secondsLeft--;
  if (secondsLeft < 0) {
    clearInterval(countdown);
    console.log("Time's up!");
  }
}, 1000);

    Timers are not perfectly precise

    The delay passed to setTimeout/setInterval is a minimum, not a guarantee — if the call stack is busy with other code (see Chapter 70), the callback may run later than requested. For animations, requestAnimationFrame is generally a better fit than setInterval, since it syncs with the browser's own refresh rate.

    Chapter 70

    Event Loop

    Chapter 4 introduced the event loop at a high level. Now that Part VII has covered callbacks, Promises, async/await, and timers, it's worth revisiting the event loop in full detail — it's the mechanism that ties all of them together.

    The pieces involved

    • Call stack — where currently executing code lives.
    • Web APIs — browser-provided features (timers, fetch, DOM events) that run outside the JavaScript engine.
    • Macrotask (callback) queue — holds callbacks from setTimeout, setInterval, and DOM events, waiting for the call stack to be empty.
    • Microtask queue — holds Promise callbacks (.then, .catch, await continuations); this queue is always fully emptied before the next macrotask runs.

    Why this order matters

    console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");

// Output: 1, 4, 3, 2

    Even though the setTimeout delay is 0, its callback goes into the macrotask queue, while the Promise's .then() goes into the microtask queue. All synchronous code (1, 4) runs first; then the entire microtask queue is drained (3); only then does the event loop pick up the next macrotask (2).

    Putting it all together

    This single mechanism explains: why UI stays responsive during a network request, why a chain of .then() calls always resolves in order, why nested setTimeout callbacks can be delayed under heavy load, and why await "pauses" a function without ever blocking the rest of the page.

    Teaching note: A live demo of the code example above, run in the console with predictions gathered from students beforehand, is one of the most effective ways to make the event loop concrete rather than abstract. This chapter connects Part I's introduction to how JavaScript works with everything students have built since — and sets up Part VIII, which looks at what's happening even deeper under the hood.

    Advanced JavaScript

    Chapter 71

    Execution Context

    An execution context is the environment in which JavaScript code is evaluated and run — it holds the variables, functions, and the value of this that are available at that point in the code. Every time a function is called, a brand new execution context is created for it.

    The three types

    • Global execution context — created once, when the script first runs; it's the base of everything.
    • Function execution context — created every time a function is invoked, one per call.
    • Eval execution context — created by code run inside eval(), rarely used in modern code.

    What a context contains

    Each execution context is built in two phases. In the creation phase, JavaScript scans the code, sets up memory for variables and functions (this is what produces hoisting, see Chapter 15), and determines the value of this. In the execution phase, the code actually runs line by line, assigning real values to those variables.

    function greet(name) {
  var message = "Hello, " + name; // created (as undefined) in creation phase,
  console.log(message);           // assigned in execution phase
}
greet("Ada");

    Contexts and scope

    Each function execution context also stores a reference to its outer environment — this reference is exactly what makes lexical scoping (Chapter 14) and closures (Chapter 16) work: a function can still reach variables from the context it was defined in, even after that context has technically finished running.

    Teaching note: This chapter is the theoretical foundation for the call stack (Chapter 72). It helps to draw execution contexts as boxes being created and destroyed, since students often picture scope as static rather than something rebuilt on every call.
    Chapter 72

    Call Stack

    The call stack is the mechanism JavaScript uses to keep track of execution contexts (Chapter 71) — it's a simple, last-in-first-out (LIFO) structure: the most recently called function is the first one to finish and be removed.

    Watching the stack grow and shrink

    function first() {
  second();
  console.log("first done");
}
function second() {
  third();
  console.log("second done");
}
function third() {
  console.log("third done");
}
first();
// Stack: [first] -> [first, second] -> [first, second, third]
// Unwinds: "third done", "second done", "first done"

    Stack overflow

    Because the stack has a finite size, a function that calls itself without ever stopping — an infinite recursion (Chapter 17) — will eventually exhaust it:

    function loop() {
  return loop(); // no base case!
}
loop(); // Uncaught RangeError: Maximum call stack size exceeded

    The stack is single-threaded

    JavaScript has exactly one call stack, which is why it's described as single-threaded: only one piece of code can run at a time. This is precisely why long-running synchronous code freezes the page, and why asynchronous operations (Chapter 70) are handed off to Web APIs and queues instead of blocking the stack directly.

    Reading a stack trace

    function outer() { inner(); }
function inner() { throw new Error("Something broke"); }
outer();
// Error: Something broke
//   at inner (script.js:2)
//   at outer (script.js:1)
//   at script.js:3

    A stack trace is simply a snapshot of the call stack at the moment an error was thrown, read from the innermost call at the top down to the original call at the bottom — an essential tool when debugging (Chapter 20).

    Chapter 73

    Memory Management

    Every value a JavaScript program creates — variables, objects, functions — needs to live somewhere in memory. JavaScript manages this automatically, but understanding the underlying model helps explain performance issues and memory leaks.

    The memory lifecycle

    • Allocate — memory is reserved when a value is created.
    • Use — the program reads and writes to that memory.
    • Release — the memory is freed once it's no longer needed (handled by the garbage collector, Chapter 74).

    The stack vs. the heap

    Primitive values (numbers, strings, booleans, null, undefined, symbols) are typically stored on the stack — fixed-size, fast to allocate and clean up. Objects, arrays, and functions are stored on the heap — a larger, less structured region for data whose size can change or isn't known in advance.

    let age = 28;              // primitive: lives on the stack
let user = { name: "Ada" }; // object: lives on the heap,
                             // "user" on the stack just holds a reference to it

    Why this distinction matters

    let a = { value: 1 };
let b = a;       // b copies the *reference*, not the object
b.value = 2;
console.log(a.value); // 2 -- both variables point to the same heap object

    This is the same reference-vs-value behavior first introduced with objects in Chapter 21 — copying an object copies the address, not the data, which is why mutating b also affects a.

    Common causes of memory leaks

    • Forgotten timers or intervals (Chapter 69) that keep references alive.
    • Event listeners that are never removed from elements that are otherwise discarded.
    • Global variables that accumulate data indefinitely.
    • Closures (Chapter 16) that unintentionally keep large objects reachable.
    Chapter 74

    Garbage Collection

    Garbage collection is the automatic process the JavaScript engine uses to find and free memory (Chapter 73) that a program can no longer reach. Developers never call it directly — it runs in the background, deciding what's safe to remove.

    Reachability

    The core idea behind garbage collection is reachability: a value is kept in memory as long as it can still be accessed, starting from a set of "roots" (global variables, the currently executing functions and their local variables). Anything unreachable from those roots is eligible for collection.

    let user = { name: "Ada" };
user = null; // the object { name: "Ada" } is now unreachable
             // and becomes eligible for garbage collection

    Mark-and-sweep

    Modern engines use an algorithm called mark-and-sweep: starting from the roots, the collector marks every value it can reach, then sweeps away everything left unmarked. This correctly handles even values that reference each other in a cycle, as long as nothing external still points to them.

    function makeCycle() {
  const objA = {};
  const objB = {};
  objA.ref = objB;
  objB.ref = objA; // objA and objB reference each other
}
makeCycle();
// once makeCycle() finishes, neither object is reachable from any root,
// so mark-and-sweep collects both -- despite the circular reference

    What developers can actually do

    Since collection itself is automatic, the practical job is making sure things become unreachable when they should — clearing timers with clearInterval (Chapter 69), removing event listeners that are no longer needed, and avoiding unnecessary global variables (Chapter 14).

    Teaching note: A useful framing for students: garbage collection doesn't prevent memory leaks in JavaScript — it only collects what's truly unreachable. A leak happens when code keeps an accidental reference alive, not when the collector "fails."
    Chapter 75

    Prototype

    Every JavaScript object has a hidden, internal link to another object called its prototype. When a property or method isn't found directly on an object, JavaScript automatically looks for it on the prototype instead. This single mechanism is how inheritance works in JavaScript.

    Every object has one

    const user = { name: "Ada" };
console.log(user.toString()); // "[object Object]"
// toString isn't defined on "user" itself -- it's found on its prototype

    Accessing an object's prototype

    const user = { name: "Ada" };
console.log(Object.getPrototypeOf(user) === Object.prototype); // true
console.log(user.__proto__ === Object.prototype); // same thing, older syntax

    Object.getPrototypeOf() is the modern, recommended way to read a prototype; __proto__ still works in every browser but is considered legacy.

    Functions have a prototype property, too

    function Person(name) {
  this.name = name;
}
Person.prototype.greet = function () {
  return `Hi, I'm ${this.name}`;
};

const ada = new Person("Ada");
console.log(ada.greet()); // "Hi, I'm Ada"
// greet() lives once on Person.prototype, shared by every instance

    This is the mechanism behind constructor functions (Chapter 82): every instance created with new Person() gets its own name, but they all share the exact same greet function through the prototype, saving memory.

    Setting a prototype directly

    const animal = { eats: true };
const rabbit = Object.create(animal); // rabbit's prototype is "animal"
console.log(rabbit.eats); // true, inherited
    Chapter 76

    Prototype Chain

    Since a prototype (Chapter 75) is itself an object, it can have its own prototype — and that one can have another. This linked sequence is the prototype chain, and it's what JavaScript walks through when looking up a property.

    Walking the chain

    const rabbit = { jumps: true };
const whiteRabbit = Object.create(rabbit);
whiteRabbit.color = "white";

console.log(whiteRabbit.color); // "white" -- found directly on whiteRabbit
console.log(whiteRabbit.jumps); // true    -- not found directly, so JS checks its prototype: rabbit
console.log(whiteRabbit.toString); // function -- not on rabbit either, so JS checks *its* prototype: Object.prototype

    The chain always ends at null

    console.log(Object.getPrototypeOf(Object.prototype)); // null

    Object.prototype is the final link in nearly every chain; its own prototype is null, which is where the lookup stops. If a property isn't found anywhere along the chain, the result is simply undefined.

    Checking where a property comes from

    console.log(whiteRabbit.hasOwnProperty("color")); // true  -- defined directly on the object
console.log(whiteRabbit.hasOwnProperty("jumps")); // false -- inherited from the chain
console.log("jumps" in whiteRabbit);              // true  -- "in" checks the whole chain

    Class syntax uses the same chain underneath

    class Animal {}
class Rabbit extends Animal {}
const bugs = new Rabbit();
console.log(Object.getPrototypeOf(Rabbit.prototype) === Animal.prototype); // true

    The class and extends keywords (Chapters 38, 39) are, underneath, syntax built directly on top of prototypes and prototype chains — they don't introduce a separate inheritance system, just a cleaner way to write one.

    Teaching note: Once students see that class/extends compiles down to exactly this chain, prototype-based inheritance stops feeling like a separate, older topic and starts feeling like the mechanism they've already been using.
    Chapter 77

    this Keyword

    this refers to the object that is currently executing a function — but unlike most languages, its value in JavaScript isn't fixed to where a function is defined; it's determined by how the function is called.

    Four ways this gets set

    // 1. Method call -- "this" is the object before the dot
const user = {
  name: "Ada",
  greet() { return `Hi, I'm ${this.name}`; },
};
user.greet(); // this === user

// 2. Plain function call -- "this" is undefined in strict mode (Chapter 19)
function show() { console.log(this); }
show(); // undefined (strict mode) or the global object (sloppy mode)

// 3. Constructor call -- "this" is the newly created object
function Person(name) { this.name = name; }
const ada = new Person("Ada"); // this === ada

// 4. Explicit binding -- "this" is whatever is passed in
function greet() { return `Hi, I'm ${this.name}`; }
greet.call({ name: "Grace" }); // this === { name: "Grace" }

    The classic pitfall: losing this

    const user = {
  name: "Ada",
  greet() { return `Hi, I'm ${this.name}`; },
};
const detached = user.greet;
detached(); // "Hi, I'm undefined" -- called without "user.", so the link is lost

    Arrow functions don't have their own this

    const user = {
  name: "Ada",
  greetLater() {
    setTimeout(() => {
      console.log(`Hi, I'm ${this.name}`); // works! arrow function keeps outer "this"
    }, 1000);
  },
};
user.greetLater(); // "Hi, I'm Ada"

    Arrow functions (Chapter 33) don't create their own this — they capture it lexically from the surrounding scope at the time they're defined, which is exactly why they're so useful inside callbacks like the one above.

    Chapter 78

    bind(), call(), apply()

    bind(), call(), and apply() are three built-in methods every function has, and each one lets you explicitly control what this (Chapter 77) refers to when the function runs.

    call() — invoke immediately, arguments listed individually

    function greet(greeting) {
  return `${greeting}, I'm ${this.name}`;
}
const user = { name: "Ada" };
greet.call(user, "Hello"); // "Hello, I'm Ada"

    apply() — invoke immediately, arguments as an array

    function greet(greeting, punctuation) {
  return `${greeting}, I'm ${this.name}${punctuation}`;
}
greet.apply(user, ["Hi", "!"]); // "Hi, I'm Ada!"

    call() and apply() do exactly the same thing — the only difference is how arguments are passed. Since the spread operator (Chapter 34) can turn an array into individual arguments, apply() is rarely needed in modern code, but it still appears in older codebases.

    bind() — don't invoke, return a new function

    const boundGreet = greet.bind(user, "Hey");
boundGreet("?"); // "Hey, I'm Ada?" -- callable later, "this" is permanently locked to "user"

    bind() is the fix for the "losing this" problem

    const user = {
  name: "Ada",
  greet() { return `Hi, I'm ${this.name}`; },
};
const detached = user.greet.bind(user); // lock "this" before detaching
detached(); // "Hi, I'm Ada" -- works correctly now, unlike Chapter 77's example

    call()YesListed individually
    apply()YesAs an array
    bind()No — returns a new functionListed individually
    Chapter 79

    Symbols

    A Symbol is a primitive data type introduced in ES6, alongside strings, numbers, and booleans (Chapter 8). Every symbol created is guaranteed to be completely unique — even two symbols created with the exact same description are never equal.

    Creating a symbol

    const id1 = Symbol("id");
const id2 = Symbol("id");
console.log(id1 === id2); // false -- always unique, description is just for debugging

    Using symbols as property keys

    const id = Symbol("id");
const user = {
  name: "Ada",
  [id]: 12345, // a symbol used as a computed property key
};
console.log(user[id]); // 12345

    Because a symbol is guaranteed unique, using one as a property key is a safe way to add data to an object without any risk of colliding with an existing property name — useful when extending objects you don't fully control.

    Symbols are hidden from normal enumeration

    console.log(Object.keys(user));        // ["name"] -- symbol key is skipped
console.log(JSON.stringify(user));     // '{"name":"Ada"}' -- also skipped
console.log(Object.getOwnPropertySymbols(user)); // [Symbol(id)] -- retrievable explicitly

    Well-known symbols

    JavaScript itself uses a handful of built-in symbols to let objects customize core language behavior — the most common being Symbol.iterator, which defines how an object behaves in a for...of loop, covered next in Chapter 80.

    const range = {
  from: 1,
  to: 3,
  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;
    return {
      next() {
        return current <= last
          ? { value: current++, done: false }
          : { value: undefined, done: true };
      },
    };
  },
};
console.log([...range]); // [1, 2, 3]
    Chapter 80

    Iterators and Generators

    An iterator is any object that implements a next() method returning { value, done }, giving a standard way to produce a sequence of values one at a time. A generator is a special kind of function that makes writing iterators dramatically simpler.

    The iterator protocol, by hand

    function makeCounter(max) {
  let current = 0;
  return {
    next() {
      return current < max
        ? { value: current++, done: false }
        : { value: undefined, done: true };
    },
  };
}
const counter = makeCounter(3);
console.log(counter.next()); // { value: 0, done: false }
console.log(counter.next()); // { value: 1, done: false }
console.log(counter.next()); // { value: 2, done: false }
console.log(counter.next()); // { value: undefined, done: true }

    This is the exact same protocol used behind the scenes by Chapter 79's Symbol.iterator example — and it's what makes an object usable in a for...of loop or with the spread operator.

    Generators: the easier way

    function* makeCounter(max) {
  for (let i = 0; i < max; i++) {
    yield i; // pauses here, returning "i", until next() is called again
  }
}
const counter = makeCounter(3);
console.log(counter.next()); // { value: 0, done: false }
console.log([...makeCounter(3)]); // [0, 1, 2]

    A generator function, marked with function*, automatically implements the iterator protocol. Each call to yield pauses execution and hands back a value, resuming exactly where it left off the next time next() is called — something a normal function can't do.

    Generators can receive values back

    function* chat() {
  const name = yield "What's your name?";
  yield `Nice to meet you, ${name}`;
}
const convo = chat();
console.log(convo.next().value);        // "What's your name?"
console.log(convo.next("Ada").value);   // "Nice to meet you, Ada"

    for...of works with any iterable

    for (const num of makeCounter(3)) {
  console.log(num); // 0, 1, 2
}
    Teaching note: Generators are a natural bridge to async/await (Chapter 63) — both let a function "pause" mid-execution, one manually via yield, the other automatically around Promises.

    Object-Oriented JavaScript

    Chapter 81

    OOP Concepts

    Object-oriented programming (OOP) is a way of structuring code around objects that bundle together data (properties) and behavior (methods), rather than around a sequence of standalone functions. JavaScript supports OOP, built on the prototype system from Chapters 75 and 76.

    The four pillars

    • Encapsulation (Chapter 83) — bundling data and the methods that operate on it, hiding internal details.
    • Abstraction (Chapter 85) — exposing only what's necessary, hiding complexity behind a simple interface.
    • Inheritance (Chapter 39) — letting one class reuse and extend the behavior of another.
    • Polymorphism (Chapter 84) — letting different objects respond to the same method call in their own way.

    A small object-oriented example

    class Animal {
  constructor(name) {
    this.name = name;
  }
  speak() {
    return `${this.name} makes a sound.`;
  }
}
class Dog extends Animal {
  speak() {
    return `${this.name} barks.`;
  }
}
const generic = new Animal("Creature");
const rex = new Dog("Rex");
console.log(generic.speak()); // "Creature makes a sound."
console.log(rex.speak());     // "Rex barks."

    Why use OOP

    Organizing code as objects tends to make large programs easier to reason about: related data and behavior stay together, changes are localized, and shared behavior can be written once and reused, rather than repeated everywhere it's needed. The rest of Part IX explores each of these ideas, plus common design patterns (Chapter 87) that recur across OOP codebases.

    Teaching note: OOP isn't the only way to structure code — functional programming, covered implicitly throughout Parts I–IV via array methods and pure functions, is a real alternative. Framing OOP as "one useful toolset" rather than "the correct way" sets up healthier expectations.
    Chapter 82

    Constructors

    A constructor is a function (or class method) responsible for creating and initializing a new object. JavaScript offers two equivalent ways to write one: the older constructor function, and the modern class syntax.

    Constructor functions

    function Person(name, age) {
  this.name = name;
  this.age = age;
}
Person.prototype.introduce = function () {
  return `I'm ${this.name}, age ${this.age}`;
};
const ada = new Person("Ada", 28);
console.log(ada.introduce()); // "I'm Ada, age 28"

    The new keyword does four things automatically: it creates a brand-new empty object, sets that object's prototype (Chapter 75) to Person.prototype, calls the function with this bound to the new object, and returns that object.

    Class constructors

    class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }
  introduce() {
    return `I'm ${this.name}, age ${this.age}`;
  }
}
const ada = new Person("Ada", 28); // identical result to the function version above

    As Chapter 76 established, this is the same mechanism as the constructor function above — class (Chapter 38) is syntax sugar over prototypes, and constructor() is simply the special method that runs when new is used.

    Forgetting new

    function Person(name) { this.name = name; }
const oops = Person("Ada"); // called without "new"
console.log(oops); // undefined -- "this" wasn't bound to a new object

class Person2 { constructor(name) { this.name = name; } }
Person2("Ada"); // TypeError: Class constructor Person2 cannot be invoked without 'new'

    Class constructors throw an error if called without new, which is one of the small safety improvements class syntax offers over plain constructor functions.

    Default parameter values

    class Person {
  constructor(name, age = 18) { // default parameters, Chapter 13
    this.name = name;
    this.age = age;
  }
}
console.log(new Person("Ada").age); // 18
    Chapter 83

    Encapsulation

    Encapsulation means bundling an object's data with the methods that operate on it, and restricting direct access to some of that data from outside — protecting an object's internal state from being changed in invalid or unexpected ways.

    The problem encapsulation solves

    class BankAccount {
  constructor(balance) {
    this.balance = balance; // fully public -- anyone can set it directly
  }
}
const account = new BankAccount(100);
account.balance = -9999; // nothing stops this invalid state

    Private fields

    class BankAccount {
  #balance; // private field, Chapter 40 -- only accessible inside this class

  constructor(balance) {
    this.#balance = balance;
  }
  deposit(amount) {
    if (amount <= 0) throw new Error("Deposit must be positive");
    this.#balance += amount;
  }
  getBalance() {
    return this.#balance;
  }
}
const account = new BankAccount(100);
account.deposit(50);
console.log(account.getBalance()); // 150
console.log(account.#balance); // SyntaxError: Private field '#balance' must be declared in an enclosing class

    The # prefix (Chapter 40) makes #balance genuinely inaccessible from outside the class — not just hidden by convention, but enforced by the language itself.

    Getters and setters

    class BankAccount {
  #balance;
  constructor(balance) { this.#balance = balance; }
  get balance() {                  // reads like a property: account.balance
    return this.#balance;
  }
  set balance(value) {             // writes like a property, but runs validation
    if (value < 0) throw new Error("Balance cannot be negative");
    this.#balance = value;
  }
}
const account = new BankAccount(100);
account.balance = 200;   // runs the setter
console.log(account.balance); // runs the getter -> 200

    Getters and setters give external code the convenience of plain property access, while still letting the class control and validate what actually happens underneath.

    Chapter 84

    Polymorphism

    Polymorphism — literally "many forms" — means objects of different classes can be used through the same interface, with each one responding to the same method call in its own way.

    Method overriding

    class Shape {
  area() {
    return 0;
  }
}
class Circle extends Shape {
  constructor(radius) { super(); this.radius = radius; }
  area() { return Math.PI * this.radius ** 2; } // overrides Shape's area()
}
class Square extends Shape {
  constructor(side) { super(); this.side = side; }
  area() { return this.side ** 2; } // a different override
}
const shapes = [new Circle(3), new Square(4)];
shapes.forEach((shape) => console.log(shape.area().toFixed(2)));
// 28.27
// 16.00

    The loop above calls shape.area() identically for every item, but each object runs its own version — the caller doesn't need to know or check which specific class it's dealing with.

    Why this is useful

    function totalArea(shapes) {
  return shapes.reduce((sum, shape) => sum + shape.area(), 0);
  // works for Circle, Square, or any future Shape subclass --
  // this function never needs to change to support a new shape
}

    Duck typing

    JavaScript doesn't require objects to share a common parent class to be used polymorphically — if an object has the method being called, it works, regardless of inheritance. This informal style is often called "duck typing": if it walks like a duck and quacks like a duck, treat it like a duck.

    const notEvenAShape = { area: () => 99 };
console.log(totalArea([new Circle(1), notEvenAShape])); // works fine
    Chapter 85

    Abstraction

    Abstraction means exposing only the essential, relevant parts of an object's behavior while hiding the complex implementation details behind it. Encapsulation (Chapter 83) is the mechanism; abstraction is the goal it's used for.

    A familiar, everyday example

    const response = await fetch("/api/users"); // Chapter 64
const data = await response.json();

    Calling fetch() hides an enormous amount of complexity — DNS lookups, TCP connections, TLS handshakes, parsing HTTP responses — behind two simple method calls. That's abstraction: a simple interface standing in front of real complexity.

    Building your own abstraction

    class Database {
  #connection;
  constructor(config) {
    this.#connection = this.#connect(config); // complex setup, hidden
  }
  #connect(config) {
    // imagine dozens of lines handling sockets, auth, retries...
    return { status: "connected", config };
  }
  query(sql) {
    // the only thing the outside world needs to know about
    return `Executing: ${sql}`;
  }
}
const db = new Database({ host: "localhost" });
console.log(db.query("SELECT * FROM users"));
// Callers never see #connect() or #connection directly

    Abstraction vs. encapsulation

    EncapsulationAbstraction
    The technique: bundling data with behavior, restricting accessThe goal: hiding complexity behind a simple interface
    Answers: "how is it protected?"Answers: "what does the user actually need to see?"

    In practice the two work together: private fields and methods (Chapter 83) are the tool; a clean, minimal public API is the result.

    Chapter 86

    Composition

    Composition builds new objects by combining smaller, focused pieces of behavior, rather than by extending a class hierarchy (Chapter 39). It's often summarized as "favor composition over inheritance" — a widely cited guideline in object-oriented design.

    The problem with deep inheritance

    class Bird { fly() { return "flying"; } }
class Penguin extends Bird { } // penguins can't actually fly!
new Penguin().fly(); // "flying" -- logically wrong, but inherited anyway

    Inheritance forces every subclass to accept everything the parent gives it, even behavior that doesn't make sense — a classic sign that composition may fit the problem better.

    Composing behavior instead

    const canFly = (state) => ({
  fly: () => `${state.name} is flying`,
});
const canSwim = (state) => ({
  swim: () => `${state.name} is swimming`,
});

function createDuck(name) {
  const state = { name };
  return { ...state, ...canFly(state), ...canSwim(state) };
}
function createPenguin(name) {
  const state = { name };
  return { ...state, ...canSwim(state) }; // no canFly -- correctly excluded
}
const duck = createDuck("Donald");
console.log(duck.fly());  // "Donald is flying"
const penguin = createPenguin("Pingu");
console.log(penguin.swim()); // "Pingu is swimming"
console.log(penguin.fly); // undefined -- never composed in

    Each small function (canFly, canSwim) describes one capability, and an object is built by combining exactly the ones it needs, using the spread operator (Chapter 34) — there's no shared ancestor forcing unrelated behavior onto every subtype.

    Composition with classes

    class Engine {
  start() { return "Engine started"; }
}
class Car {
  constructor() {
    this.engine = new Engine(); // Car "has an" Engine, rather than "is an" Engine
  }
  start() {
    return this.engine.start();
  }
}

    This "has-a" relationship, instead of "is-a" inheritance, keeps Engine reusable in other classes (a Boat, a Generator) without forcing them into a shared, and increasingly awkward, class hierarchy.

    Chapter 87

    Design Patterns

    A design pattern is a reusable, well-known solution to a recurring software design problem — not finished code to copy and paste, but a proven shape a solution can take. This chapter covers a handful of the most common patterns seen in JavaScript.

    Singleton — exactly one instance

    class Settings {
  static #instance;
  constructor() {
    if (Settings.#instance) return Settings.#instance;
    this.theme = "dark";
    Settings.#instance = this;
  }
}
const a = new Settings();
const b = new Settings();
console.log(a === b); // true -- always the same instance

    Factory — centralize object creation

    function createUser(type, name) {
  if (type === "admin") return { name, permissions: ["read", "write", "delete"] };
  return { name, permissions: ["read"] };
}
const admin = createUser("admin", "Ada");
const guest = createUser("guest", "Grace");

    Observer — notify subscribers of changes

    class EventEmitter {
  #listeners = {};
  on(event, callback) {
    (this.#listeners[event] ??= []).push(callback);
  }
  emit(event, data) {
    (this.#listeners[event] || []).forEach((callback) => callback(data));
  }
}
const emitter = new EventEmitter();
emitter.on("login", (user) => console.log(`${user} logged in`));
emitter.emit("login", "Ada"); // "Ada logged in"

    This is the same pattern browsers use internally for addEventListener (Chapter 50) — a subject keeps a list of listeners and notifies all of them when something happens.

    Module — encapsulate private state

    const counterModule = (() => {
  let count = 0; // private, only reachable through the closure (Chapter 16)
  return {
    increment: () => ++count,
    getCount: () => count,
  };
})();
counterModule.increment();
console.log(counterModule.getCount()); // 1
console.log(counterModule.count); // undefined -- truly private

    This pattern predates ES6 modules (Chapter 37) and private fields (Chapter 40), and relies purely on closures to hide state — it's still common in older codebases and libraries.

    Teaching note: Patterns are tools for specific problems, not goals in themselves. Encourage students to recognize a problem first ("I need exactly one shared instance"), then reach for the matching pattern — not the reverse.
    Chapter 88

    SOLID Principles

    SOLID is an acronym for five design principles that help keep object-oriented code maintainable, flexible, and easy to extend as it grows. They originated in class-based languages but apply just as well to JavaScript.

    S — Single Responsibility

    A class should have exactly one reason to change — one clear job.

    // Avoid: one class doing two unrelated jobs
class User {
  constructor(name) { this.name = name; }
  save() { /* database logic */ }
}

// Prefer: split into focused classes
class User {
  constructor(name) { this.name = name; }
}
class UserRepository {
  save(user) { /* database logic, separated out */ }
}

    O — Open/Closed

    Code should be open to extension but closed to modification — new behavior should be addable without editing existing, working code. This is exactly what polymorphism (Chapter 84) enables: adding a new Shape subclass never requires changing totalArea().

    L — Liskov Substitution

    A subclass should be usable anywhere its parent class is expected, without breaking anything. Chapter 86's flying-penguin example is a Liskov violation: Penguin can't safely stand in for every place a Bird is used.

    I — Interface Segregation

    // Avoid: one big interface forcing unused methods on everyone
class Worker {
  work() {}
  eat() {}
}
class Robot extends Worker {
  eat() { throw new Error("Robots don't eat!"); } // forced to implement something irrelevant
}

// Prefer: smaller, focused interfaces -- composition (Chapter 86) helps here
const canWork = { work: () => "working" };
const canEat = { eat: () => "eating" };
const robot = { ...canWork }; // only takes what applies

    D — Dependency Inversion

    // Avoid: tightly coupled to one specific implementation
class Notifier {
  constructor() { this.emailService = new EmailService(); }
}

// Prefer: depend on an abstraction, passed in
class Notifier {
  constructor(service) { this.service = service; } // any service with a .send() method works
}
new Notifier(new EmailService());
new Notifier(new SmsService()); // swapped freely, Notifier never changes

    High-level code shouldn't depend on specific low-level details — both should depend on a shared, simple interface instead, which keeps components swappable and easier to test.

    Chapter 89

    MVC Pattern

    MVC (Model–View–Controller) is an architectural pattern that separates an application into three connected parts, each with a single responsibility — a direct application of the Single Responsibility principle from Chapter 88, applied to an entire application's structure.

    The three parts

    • Model — owns the data and business logic, with no knowledge of how it's displayed.
    • View — renders the UI, displaying whatever data the Model provides.
    • Controller — handles user input, updates the Model, and tells the View to refresh.

    A minimal MVC example

    // Model
class TodoModel {
  #todos = [];
  add(text) { this.#todos.push({ text, done: false }); }
  getAll() { return this.#todos; }
}

// View
class TodoView {
  render(todos) {
    console.log("--- Todo List ---");
    todos.forEach((t) => console.log(`[${t.done ? "x" : " "}] ${t.text}`));
  }
}

// Controller
class TodoController {
  constructor(model, view) {
    this.model = model;
    this.view = view;
  }
  addTodo(text) {
    this.model.add(text);       // updates the Model
    this.view.render(this.model.getAll()); // tells the View to re-render
  }
}

const controller = new TodoController(new TodoModel(), new TodoView());
controller.addTodo("Learn MVC");
controller.addTodo("Build a todo app");

    Why separate these concerns

    The Model never imports or references the View, and the View never contains business logic — each piece can be tested, changed, or even completely replaced (a new UI framework, a different storage backend) without rewriting the others.

    Teaching note: DOM-based code from Part V naturally tends to mix all three concerns into one script. Rewriting a small DOM project using this chapter's structure is a concrete way to make the separation click.
    Chapter 90

    MVVM Pattern

    MVVM (Model–View–ViewModel) is a variation on MVC (Chapter 89), built around one key difference: instead of a Controller manually updating the View, a ViewModel exposes data that the View binds to directly, updating automatically whenever that data changes.

    The three parts

    • Model — the raw data, same role as in MVC.
    • View — the UI, but instead of being told what to render, it observes and reacts to the ViewModel.
    • ViewModel — holds UI-ready state and logic, and notifies the View automatically when that state changes — this automatic sync is called data binding.

    A simplified data-binding example

    class ViewModel {
  #listeners = [];
  #count = 0;
  get count() { return this.#count; }
  set count(value) {
    this.#count = value;
    this.#listeners.forEach((fn) => fn(value)); // notify the View automatically
  }
  onChange(callback) {
    this.#listeners.push(callback);
  }
}

const vm = new ViewModel();
vm.onChange((value) => {
  document.querySelector("#count").textContent = value; // the "View" reacting
});

document.querySelector("#increment").addEventListener("click", () => {
  vm.count++; // the View never manually calls a render function --
});           // setting the data is enough

    Compare this to Chapter 89's TodoController, which had to explicitly call view.render() after every change — here, changing vm.count is the only step needed; the View updates itself as a side effect of the binding.

    Where MVVM shows up

    MVVM is the underlying model behind most modern front-end frameworks: a component's reactive state acts as the ViewModel, and the framework's rendering system handles binding it to the DOM automatically, removing the need to write manual DOM updates like those in Part V.

    MVC vs. MVVM

    MVCMVVM
    Controller manually updates the ViewView automatically syncs via data binding
    More explicit, more manual codeLess boilerplate, but binding can feel implicit
    Common in traditional server-rendered appsCommon in modern reactive front-end frameworks

    Drag and Drop

    The Drag and Drop API lets users pick up an element with the mouse and drop it somewhere else on the page, coordinated through a specific sequence of events fired on both the dragged element and the drop target.

    Making an element draggable

    <div id="card" draggable="true">Drag me</div>
<div id="dropzone">Drop here</div>

    Events on the dragged element

    const card = document.querySelector("#card");
card.addEventListener("dragstart", (event) => {
  event.dataTransfer.setData("text/plain", event.target.id); // store what's being dragged
  card.classList.add("dragging"); // Chapter 44
});
card.addEventListener("dragend", () => card.classList.remove("dragging"));

    Events on the drop target

    const dropzone = document.querySelector("#dropzone");
dropzone.addEventListener("dragover", (event) => {
  event.preventDefault(); // required -- drop is blocked by default without this
});
dropzone.addEventListener("drop", (event) => {
  event.preventDefault();
  const id = event.dataTransfer.getData("text/plain");
  const draggedEl = document.getElementById(id);
  dropzone.appendChild(draggedEl); // Chapter 45
});

    The single most common bug with drag and drop is forgetting event.preventDefault() inside dragover — without it, the browser's default behavior (usually rejecting the drop) takes over and drop never fires.

    A practical use: reordering a list

    document.querySelectorAll(".list-item").forEach((item) => {
  item.addEventListener("dragstart", (e) => e.dataTransfer.setData("text/plain", item.dataset.id));
});
list.addEventListener("drop", (event) => {
  event.preventDefault();
  const id = event.dataTransfer.getData("text/plain");
  const dragged = list.querySelector(`[data-id="${id}"]`);
  list.insertBefore(dragged, event.target); // Chapter 47
});

    Geolocation API

    The Geolocation API lets a web page request the user's physical location, with the browser handling the underlying GPS, Wi-Fi, or IP-based lookup. Access always requires explicit user permission.

    Getting the current position

    navigator.geolocation.getCurrentPosition(
  (position) => {
    const { latitude, longitude, accuracy } = position.coords;
    console.log(`Lat: ${latitude}, Lng: ${longitude}, accurate to ${accuracy}m`);
  },
  (error) => {
    console.error("Location error:", error.message); // e.g. permission denied
  }
);

    getCurrentPosition takes two callbacks — a success handler and an error handler — making it one of the few modern browser APIs that still uses the older callback style (Chapter 61) rather than returning a Promise.

    Watching position over time

    const watchId = navigator.geolocation.watchPosition((position) => {
  console.log("Moved to:", position.coords.latitude, position.coords.longitude);
});

navigator.geolocation.clearWatch(watchId); // stop watching, similar to clearInterval (Chapter 69)

    Passing options

    navigator.geolocation.getCurrentPosition(success, error, {
  enableHighAccuracy: true, // prefer GPS over faster, less precise methods
  timeout: 5000,            // give up after 5 seconds
  maximumAge: 60000,        // accept a cached position up to 1 minute old
});

    Handling permission gracefully

    if (!("geolocation" in navigator)) {
  console.log("Geolocation is not supported by this browser");
} else {
  navigator.geolocation.getCurrentPosition(success, (error) => {
    if (error.code === error.PERMISSION_DENIED) {
      console.log("User denied location access -- show a manual location input instead");
    }
  });
}
    Teaching note: Geolocation only works on secure origins (HTTPS or localhost) in modern browsers — a frequent surprise when a demo works locally but silently fails once deployed over plain HTTP.

    Notifications API

    The Notifications API lets a web page display system-level notifications — the same kind of alert a desktop app or the operating system itself might show — even when the browser tab isn't focused.

    Requesting permission

    async function askPermission() {
  const permission = await Notification.requestPermission(); // "granted", "denied", or "default"
  console.log(permission);
}
askPermission();

    Like geolocation (Chapter 95), notifications always require explicit, user-initiated permission — browsers block sites from requesting it automatically on page load to prevent abuse.

    Showing a notification

    if (Notification.permission === "granted") {
  const notification = new Notification("New message", {
    body: "Ada sent you a message.",
    icon: "/icon.png",
  });
  notification.addEventListener("click", () => {

}

    async function notifyUser(title, options) {

}
notifyUser("Task complete", { body: "Your export finished." });

    Chapter 97

    Web Workers

    A Web Worker runs JavaScript on a separate background thread, away from the main thread that handles the UI. This is how JavaScript, despite the single-threaded call stack from Chapter 72, can still run heavy computation without freezing the page.

    Creating a worker

    // main.js
const worker = new Worker("worker.js");
worker.postMessage({ command: "start", n: 40 }); // send data to the worker
    // worker.js
self.addEventListener("message", (event) => {
  const { n } = event.data;
  const result = fibonacci(n); // a slow, CPU-heavy computation
  self.postMessage(result);    // send the result back
});
function fibonacci(n) {
  return n <= 1 ? n : fibonacci(n - 1) + fibonacci(n - 2);
}

    Receiving the result on the main thread

    worker.addEventListener("message", (event) => {
  console.log("Result:", event.data);
});
worker.addEventListener("error", (event) => {
  console.error("Worker error:", event.message);
});

    Why workers exist

    // Without a worker: this blocks the entire page, freezing scroll, clicks, animation
const result = fibonacci(40);

// With a worker: the main thread stays fully responsive while it computes
worker.postMessage({ command: "start", n: 40 });

    What workers can't do

    Workers run in an isolated global scope with no access to the DOM, window, or the parent page's variables — communication only happens through postMessage, passing copies of data back and forth rather than sharing memory directly.

    worker.terminate(); // stop the worker entirely when it's no longer needed
    Teaching note: Workers solve a different problem than async/await (Chapter 63). Async code frees the main thread while waiting on something else (a network response); a worker frees it while actually computing something CPU-intensive. Neither replaces the other.
    Chapter 98

    Service Workers

    A service worker is a special kind of Web Worker (Chapter 97) that sits between a web app and the network, able to intercept requests, cache responses, and keep an app working even when the user is offline.

    Registering a service worker

    // main.js
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js")
    .then((registration) => console.log("Service worker registered:", registration.scope))
    .catch((error) => console.error("Registration failed:", error));
}

    Caching files on install

    // sw.js
const CACHE_NAME = "app-cache-v1";
const FILES_TO_CACHE = ["/", "/index.html", "/styles.css", "/app.js"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(FILES_TO_CACHE))
  );
});

    Serving from cache, falling back to the network

    self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});

    This fetch handler is what makes a page work offline: every request the page makes is intercepted first, and served from the cache if it's there — the same fetch concept from Chapter 64, just running inside the service worker instead of the page.

    Cleaning up old caches

    self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((key) => key !== CACHE_NAME).map((key) => caches.delete(key)))
    )
  );
});

    The service worker lifecycle

    A service worker moves through distinct events — install (set up the cache), activate (clean up old versions), and fetch (intercept every network request) — and runs independently of any single open tab, which is exactly what makes background caching and, later, push notifications possible.

    Progressive Web Apps

    A Progressive Web App (PWA) is a website built to feel and behave like a native app — installable, capable of working offline, and able to launch from a home screen icon — built entirely from the web technologies already covered, with no separate native codebase.

    The three core ingredients

    • HTTPS — PWAs require a secure connection, the same requirement noted for geolocation in Chapter 95.
    • A service worker (Chapter 98) — enables offline support and background behavior.
    • A web app manifest — a JSON file describing the app's name, icons, and how it should appear when installed.

    IndexedDB

    IndexedDB is a full, transactional database built into the browser — far more capable than localStorage (Chapter 57), suited to storing large amounts of structured data, including objects, files, and blobs, entirely offline.

    Opening a database

    const request = indexedDB.open("TaskDB", 1); // database name, version number

request.addEventListener("upgradeneeded", (event) => {
  const db = event.target.result;
  const store = db.createObjectStore("tasks", { keyPath: "id", autoIncrement: true });
  store.createIndex("byStatus", "status"); // an index for fast lookups later
});

request.addEventListener("success", (event) => {
  const db = event.target.result;
  console.log("Database ready");
});
request.addEventListener("error", (event) => {
  console.error("Database error:", event.target.error);
});

    The upgradeneeded event fires only when the database is first created, or when the version number increases — it's the one place object stores and indexes can be created or changed.

    Adding data

    function addTask(db, task) {
  const tx = db.transaction("tasks", "readwrite"); // every operation happens inside a transaction
  const store = tx.objectStore("tasks");
  store.add(task);
}
addTask(db, { text: "Learn IndexedDB", status: "pending" });

    Reading data

    function getAllTasks(db) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("tasks", "readonly");
    const request = tx.objectStore("tasks").getAll();
    request.addEventListener("success", () => resolve(request.result));
    request.addEventListener("error", () => reject(request.error));
  });
}

    Wrapping IndexedDB's callback-based, event-driven API in a Promise, as above, is extremely common — it lets the rest of the app use the same async/await style from Chapter 63 instead of nested event listeners.

    Updating and deleting

    function updateTask(db, task) {
  const tx = db.transaction("tasks", "readwrite");
  tx.objectStore("tasks").put(task); // put() overwrites an existing record by key
}
function deleteTask(db, id) {
  const tx = db.transaction("tasks", "readwrite");
  tx.objectStore("tasks").delete(id);
}

    PART XI

    JavaScript Security

    Chapter 101

    Cross-Site Scripting (XSS)

    Cross-Site Scripting (XSS) is a vulnerability where an attacker manages to inject and run their own JavaScript inside a page a victim trusts — letting that script read cookies, steal session data, or act on the page as if it were the victim themselves.

    How it happens: unsafe HTML insertion

    // A comment form that trusts user input completely
const comment = getUserInput(); // e.g. <img src=x onerror="stealCookies()">
commentBox.innerHTML = comment; // Chapter 43 -- innerHTML runs any script/tag inside it

    If comment comes directly from another user — a form field, a URL parameter, a stored database record — and is inserted with innerHTML unmodified, any HTML or script it contains executes exactly as if it were part of the original page.

    The three common types

    • Stored XSS — malicious input is saved (e.g. in a database) and served to every future visitor, such as a comment field like the one above.
    • Reflected XSS — malicious input comes from the current request itself, often a URL parameter, and is immediately echoed back into the page.
    • DOM-based XSS — the vulnerable code never touches the server at all; client-side JavaScript alone reads untrusted data and unsafely inserts it into the DOM.
    // Reflected XSS: URL -- example.com/search?q=<script>stealCookies()</script>
const query = new URLSearchParams(window.location.search).get("q");
resultsHeading.innerHTML = `Results for: ${query}`; // executes the injected script

    Defense: prefer textContent over innerHTML

    commentBox.textContent = comment; // Chapter 43 -- inserted as plain text, never parsed as HTML
//  now just displays as literal, harmless text

    This is the single most effective fix for the examples above: textContent never interprets its input as markup, so injected tags and event handlers simply render as visible text instead of executing.

    Defense: sanitize when HTML really is needed

    // When user content genuinely needs to allow some formatting (e.g. bold, links),
// run it through a dedicated sanitizing library rather than inserting it raw
import DOMPurify from "dompurify";
commentBox.innerHTML = DOMPurify.sanitize(comment); // strips dangerous tags/attributes, keeps safe HTML

    Defense: a Content Security Policy

    <meta http-equiv="Content-Security-Policy" content="script-src 'self'">

    A Content Security Policy (CSP) tells the browser which sources of script are allowed to run at all — with script-src 'self', even a successfully injected <script> tag from an attacker is blocked from executing, as a last line of defense behind proper input handling.

    Other habits that help

    • Treat every value from a user, URL, or external API as untrusted, no matter how it arrived.
    • Never build HTML with string concatenation or template literals (Chapter 32) from untrusted data.
    • Mark cookies that hold session data as HttpOnly, so injected script can't read them even if XSS occurs.
    Teaching note: XSS is one entry point into a much wider subject. The next chapter covers CSRF, an attack that succeeds for the opposite reason — not because the attacker's script runs on the page, but because the browser willingly attaches the victim's own credentials to a request they never meant to send.
    Chapter 102

    CSRF

    Cross-Site Request Forgery (CSRF) tricks a logged-in victim's browser into sending a request the victim never intended — not by running attacker script on the trusted page, as with XSS (Chapter 101), but by exploiting the fact that browsers attach cookies automatically to any request, no matter which site triggered it.

    How the attack works

    <!-- On attacker.com, invisible to the victim -->
<img src="https://bank.example.com/transfer?to=attacker&amount=5000" style="display:none">
<!-- The victim's browser sends this request WITH their bank.example.com session cookie attached -->

    If the bank's server trusts any request that carries a valid session cookie — without checking where the request actually came from — it processes the transfer as though the victim clicked "Send" themselves, because from the cookie's point of view, they did.

    Defense: CSRF tokens

    // Server embeds a random, unguessable token in the legitimate form
// <input type="hidden" name="csrf_token" value="a1b2c3...">

async function submitTransfer(form) {
  const formData = new FormData(form);
  const response = await fetch("/transfer", {
    method: "POST",
    body: formData, // includes csrf_token -- an attacker's forged request can't know this value
  });
  return response.json();
}

    Because the token is unpredictable and tied to the user's own session, an attacker's page has no way to read or guess it, so a forged request arrives without a valid token and the server rejects it — the fetch call itself looks identical to Chapter 60's requests, only the server-side check is new.

    Defense: SameSite cookies

    Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly
    • SameSite=Strict — the cookie is never sent on requests originating from another site, closing off the attack at the browser level.
    • SameSite=Lax — the default in modern browsers; allows the cookie on top-level navigation but blocks it on background requests like the forged <img> above.
    • HttpOnly — prevents JavaScript from reading the cookie at all, a separate protection against the XSS-driven cookie theft covered in Chapter 101.

    Defense: check the request's origin

    // Server-side check (conceptually) -- reject requests whose Origin doesn't match
if (request.headers.get("Origin") !== "https://bank.example.com") {
  return new Response("Forbidden", { status: 403 });
}
    Teaching note: XSS and CSRF are often taught back-to-back because they're frequently confused: XSS is about an attacker running code on the victim's trusted page, while CSRF is about an attacker using the victim's trusted browser to hit someone else's server. Understanding both sharpens the next chapter's broader idea of secure coding as a mindset, not just a checklist.
    Chapter 103

    Secure Coding

    Secure coding is less a single technique than a set of habits applied throughout development — treating every external input as hostile until proven otherwise, and designing so that a single mistake doesn't become a full compromise.

    Principle: never trust the client

    // Insecure: trusting a price sent from the browser
app.post("/checkout", (req, res) => {
  const { itemId, price } = req.body; // price came from the client -- anyone can change it
  chargeCard(req.user, price);
});

// Secure: the server looks up the real price itself
app.post("/checkout", (req, res) => {
  const { itemId } = req.body;
  const price = getPriceFromDatabase(itemId); // the only source of truth
  chargeCard(req.user, price);
});

    Anything that arrives over the network — form fields, URL parameters, headers, even values the client-side JavaScript computed itself — can be freely rewritten by whoever is sending the request, so decisions with real consequences must be re-verified on the server.

    Principle: least privilege

    // Give a database connection only the permissions the app actually needs
// A reporting feature that only reads data shouldn't use credentials that can also DELETE
const reportingDb = createConnection({ user: "readonly_reports", permissions: ["SELECT"] });

    Least privilege means every piece of code, credential, and user account gets the minimum access required to do its job, so that a bug or a stolen credential in one place can't cascade into control over everything.

    Principle: fail securely

    // Insecure: a broken check defaults to allowing access
function canEdit(user, doc) {
  try {
    return user.id === doc.ownerId;
  } catch {
    return true; // BAD -- an error accidentally grants access
  }
}

// Secure: a broken check defaults to denying access
function canEdit(user, doc) {
  try {
    return user.id === doc.ownerId;
  } catch {
    return false; // an error safely denies access instead
  }
}

    Principle: don't leak details in errors

    // Insecure -- reveals internal structure to whoever triggers the error
res.status(500).send(error.stack);

// Secure -- log the detail server-side, show the user something generic
console.error(error); // full detail goes to server logs only
res.status(500).send("Something went wrong. Please try again.");

    Stack traces and detailed error messages are a gift to an attacker probing an application, since they reveal file paths, library versions, and query structure that help plan a more targeted attack.

    Keep dependencies current

    npm audit          // lists known vulnerabilities in installed packages (Chapter 70)
npm audit fix       // attempts to automatically upgrade affected packages
    Teaching note: These principles — distrust the client, least privilege, fail securely, don't leak errors — recur throughout the rest of this part. The next chapter, input validation, is really the first principle put into concrete, reusable practice.
    Chapter 104

    Input Validation

    Input validation is the practice of checking that data matches what the application expects — in type, shape, length, and content — before it's used, stored, or passed along, and it's the concrete implementation of "never trust the client" from Chapter 103.

    Validating on the client (for user experience only)

    function validateSignupForm(data) {
  const errors = {};
  if (!data.email || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(data.email)) {
    errors.email = "Enter a valid email address";
  }
  if (!data.password || data.password.length < 8) {
    errors.password = "Password must be at least 8 characters";
  }
  return errors;
}

    Client-side validation like this gives instant feedback, similar to the form handling in Chapter 47, but it is easily bypassed — anyone can call the API directly with a tool like curl, skipping the browser and this check entirely.

    Validating on the server (the part that actually matters)

    function validateSignupPayload(data) {
  if (typeof data.email !== "string" || data.email.length > 254) {
    throw new Error("Invalid email");
  }
  if (typeof data.password !== "string" || data.password.length < 8) {
    throw new Error("Invalid password");
  }
  if (typeof data.age !== "number" || !Number.isInteger(data.age) || data.age < 13) {
    throw new Error("Invalid age");
  }
  return { email: data.email.trim().toLowerCase(), password: data.password, age: data.age };
}

    The server-side check re-verifies type, length, and range for every field, because it's the only validation an attacker can't skip — client-side checks are a convenience, server-side checks are the actual security boundary.

    Allowlisting over blocklisting

    // Blocklisting -- fragile, tries to guess every bad pattern
function isSafeFilenameBad(name) {
  return !name.includes("../") && !name.includes(";"); // easy to miss a case
}

// Allowlisting -- only permits known-good characters
function isSafeFilename(name) {
  return /^[a-zA-Z0-9_-]+\.(jpg|png|pdf)$/.test(name);
}

    An allowlist defines exactly what's permitted and rejects everything else, while a blocklist tries to enumerate every dangerous pattern — and there is almost always one more pattern an attacker can find that the blocklist didn't anticipate.

    Validating structured data with a schema library

    import { z } from "zod";

const SignupSchema = z.object({
  email: z.string().email().max(254),
  password: z.string().min(8),
  age: z.number().int().min(13),
});

const result = SignupSchema.safeParse(requestBody);
if (!result.success) {
  return res.status(400).json({ errors: result.error.issues });
}
const { email, password, age } = result.data; // now safe to use

    Schema libraries like Zod let validation rules be declared once and reused across the codebase, reducing the chance that one endpoint's hand-written checks drift out of sync with another's.

    Teaching note: Input validation answers "is this data well-formed?" The next two chapters answer two related but distinct questions: authentication asks "who is this?" and authorization asks "what are they allowed to do?"
    Chapter 105

    Authentication

    Authentication is the process of confirming who a user is — typically by checking a password, a token, or another proof of identity — and it's the foundation every other security topic in this part builds on: nothing else matters if the system doesn't reliably know who's making the request.

    Never store plain-text passwords

    import bcrypt from "bcrypt";

async function registerUser(email, plainPassword) {
  const passwordHash = await bcrypt.hash(plainPassword, 12); // 12 = cost factor
  await db.users.insert({ email, passwordHash }); // the plain password is never stored
}

async function verifyLogin(email, plainPassword) {
  const user = await db.users.findByEmail(email);
  if (!user) return false;
  return bcrypt.compare(plainPassword, user.passwordHash); // constant-time comparison
}

    Hashing is one-way: bcrypt.hash turns a password into a value that can be checked but never reversed back into the original, so even if the database itself leaks, the actual passwords stay protected — unlike encryption (Chapter 107), which is designed to be reversed by whoever holds the key.

    Sessions: the server remembers who's logged in

    app.post("/login", async (req, res) => {
  const user = await verifyLogin(req.body.email, req.body.password);
  if (!user) return res.status(401).send("Invalid credentials");

  req.session.userId = user.id; // stored server-side, keyed by a cookie
  res.send("Logged in");
});

app.get("/dashboard", (req, res) => {
  if (!req.session.userId) return res.status(401).send("Not logged in");
  res.send(`Welcome back, user ${req.session.userId}`);
});

    A session-based login sends the browser only an opaque, random session ID cookie, while the actual "who is this" data stays server-side — this is the traditional counterpart to the token-based approach covered in Chapter 108.

    Rate limiting login attempts

    const attempts = new Map(); // in production, use a shared store like Redis

function checkRateLimit(ip) {
  const record = attempts.get(ip) ?? { count: 0, resetAt: Date.now() + 15 * 60 * 1000 };
  if (Date.now() > record.resetAt) { record.count = 0; record.resetAt = Date.now() + 15 * 60 * 1000; }
  record.count++;
  attempts.set(ip, record);
  return record.count <= 5; // allow 5 attempts per 15 minutes
}

    Without a limit like this, an attacker can attempt thousands of password guesses per second — rate limiting turns a brute-force attack from a matter of minutes into a matter of years.

    Multi-factor authentication

    Multi-factor authentication (MFA) requires a second proof of identity beyond the password — typically a time-based one-time code from an app, or a hardware key — so that a leaked password alone isn't enough for an attacker to log in.

    Teaching note: Authentication answers "who is this user?" Once that's settled, the next chapter asks the equally important follow-up: now that we know who they are, what should they actually be allowed to do?
    Chapter 106

    Authorization

    Authorization decides what an already-authenticated user (Chapter 105) is allowed to do — a logged-in user is a known identity, but that alone says nothing about which resources they should be able to read, edit, or delete.

    The most common bug: missing an ownership check

    // Insecure -- checks that SOMEONE is logged in, but not that they own this document
app.get("/documents/:id", (req, res) => {
  if (!req.session.userId) return res.status(401).send("Not logged in");
  const doc = getDocumentById(req.params.id);
  res.json(doc); // any logged-in user can read any document by guessing its id
});

// Secure -- also verifies the document belongs to the requesting user
app.get("/documents/:id", (req, res) => {
  if (!req.session.userId) return res.status(401).send("Not logged in");
  const doc = getDocumentById(req.params.id);
  if (!doc || doc.ownerId !== req.session.userId) {
    return res.status(404).send("Not found"); // 404, not 403 -- avoids confirming it exists
  }
  res.json(doc);
});

    This class of bug, often called an Insecure Direct Object Reference, is one of the most common real-world authorization failures — the fix is never assuming that being logged in implies being permitted.

    Role-based access control (RBAC)

    const permissions = {
  viewer: ["read"],
  editor: ["read", "write"],
  admin: ["read", "write", "delete", "manage_users"],
};

function canPerform(user, action) {
  return permissions[user.role]?.includes(action) ?? false;
}

app.delete("/documents/:id", (req, res) => {
  if (!canPerform(req.user, "delete")) return res.status(403).send("Forbidden");
  deleteDocument(req.params.id);
  res.send("Deleted");
});

    RBAC groups permissions into named roles rather than checking individual users, which keeps authorization logic readable as an application grows past a handful of special cases.

    Checking authorization server-side, always

    // Insecure -- hiding a button doesn't stop a direct API call
if (user.role === "admin") {
  deleteButton.style.display = "block"; // UI-only, easily bypassed
}
// The /delete endpoint itself must repeat the check server-side, exactly as ch105/106 above show

    Hiding UI elements from users who shouldn't see them is good practice for usability, but it is never a security control on its own — anyone can open dev tools or call the API directly, so every privileged action needs its own server-side authorization check.

    Teaching note: Authentication and authorization together answer "who are you, and what can you do?" The next chapter steps back to a different question underlying much of this part: how is sensitive data itself protected, whether or not the right person is asking for it?
    Chapter 107

    Encryption Basics

    Encryption transforms readable data into unreadable ciphertext using a key, so that anyone who intercepts it — without that key — sees only meaningless bytes; unlike the password hashing in Chapter 105, encryption is deliberately reversible for whoever holds the right key.

    Encryption in transit: HTTPS

    // The browser handles this automatically for any https:// URL
fetch("https://api.example.com/account"); // encrypted end-to-end between browser and server
fetch("http://api.example.com/account");  // plain text -- readable by anyone on the network path

    HTTPS wraps every request and response covered since Chapter 60 in Transport Layer Security (TLS), so that even on an untrusted network — public Wi-Fi, a compromised router — the contents can't be read or silently altered in transit.

    Symmetric vs. asymmetric encryption

    • Symmetric encryption — the same key both encrypts and decrypts; fast, but that key must somehow be shared with the other party in advance without being intercepted.
    • Asymmetric encryption — a public key encrypts, and only the matching private key can decrypt; solves the sharing problem, since the public key can be handed out freely, but it's slower than symmetric encryption.

    In practice, HTTPS uses both: asymmetric encryption to safely exchange a temporary symmetric key when a connection first opens, then the faster symmetric key for the actual data that follows.

    Using the Web Crypto API

    async function encryptMessage(message, key) {
  const iv = crypto.getRandomValues(new Uint8Array(12)); // a unique value per encryption
  const encoded = new TextEncoder().encode(message);
  const ciphertext = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, encoded);
  return { ciphertext, iv };
}

async function generateKey() {
  return crypto.subtle.generateKey({ name: "AES-GCM", length: 256 }, true, ["encrypt", "decrypt"]);
}

    The built-in crypto.subtle API provides audited, standard implementations of algorithms like AES-GCM — hand-rolling custom encryption is a well-known way to introduce subtle, dangerous flaws, so applications should always reach for a vetted implementation like this one.

    Hashing vs. encryption — not the same thing

    Hashing (Chapter 105's bcrypt.hash) is one-way and used to verify data without storing the original; encryption is two-way and used when the original value genuinely needs to be recovered later, such as decrypting a stored file for an authorized user to view.

    Teaching note: With encryption as background, the next chapter looks at JSON Web Tokens — a format that uses the cryptographic signing techniques introduced here to let a server issue proof of identity that can be verified without a database lookup on every request.
    Chapter 108

    JWT

    A JSON Web Token (JWT) is a compact, digitally signed string that carries claims about a user — such as their ID and role — letting a server verify a request's identity without looking the session up in a database, unlike the session cookies introduced in Chapter 105.

    Anatomy of a token

    // A JWT is three base64url-encoded parts joined by dots:
// header.payload.signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiJ9.4f8a2c1b...

// Decoded header:   { "alg": "HS256", "typ": "JWT" }
// Decoded payload:  { "sub": "42", "role": "admin", "exp": 1735689600 }

    The header and payload are only base64-encoded, not encrypted, so anyone can decode and read them — a JWT's security comes entirely from the third part, the signature, which proves the token wasn't tampered with after the server issued it.

    Issuing and verifying a token

    import jwt from "jsonwebtoken";

function issueToken(user) {
  return jwt.sign(
    { sub: user.id, role: user.role },
    process.env.JWT_SECRET,        // signing key -- never exposed to the client
    { expiresIn: "1h" }
  );
}

function verifyToken(token) {
  try {
    return jwt.verify(token, process.env.JWT_SECRET); // throws if signature or expiry is invalid
  } catch {
    return null;
  }
}

    Verification recomputes the signature using the secret key and checks it matches the one on the token — if an attacker changes even a single character of the payload, such as "role":"admin", the signature no longer matches and jwt.verify rejects it.

    Using a token from the client

    const response = await fetch("/api/profile", {
  headers: { Authorization: `Bearer ${token}` }, // sent with every request
});

    Common JWT mistakes

    • Storing a JWT in localStorage makes it readable to any script on the page — a successful XSS attack (Chapter 101) can steal it directly; an HttpOnly cookie is safer.
    • Putting sensitive data in the payload — like a password or a full credit card number — is a mistake, since the payload is only encoded, not encrypted, and readable by anyone who has the token.
    • Skipping expiry (exp) means a stolen token remains valid forever; short expiry times limit the damage of a leaked token.
    Teaching note: JWTs are the mechanism; the next chapter, OAuth, is the protocol that most commonly issues them — letting a user log into one application using an identity they've already established with another, like "Sign in with Google."
    Chapter 109

    OAuth

    OAuth is a protocol that lets a user grant one application limited access to their data on another, without ever handing over their password to the first application — it's what powers buttons like "Sign in with Google" or "Connect your GitHub account."

    The problem OAuth solves

    Before OAuth, the only way for a third-party app to act on a user's behalf was for the user to type their actual password into that third-party app — a practice sometimes called the "password anti-pattern," since it hands over full account access rather than just the specific permission needed.

    The Authorization Code flow, step by step

    // 1. The app redirects the user to the provider's login/consent screen
const authUrl = `https://accounts.provider.com/authorize` +
  `?client_id=${CLIENT_ID}` +
  `&redirect_uri=${encodeURIComponent("https://myapp.com/callback")}` +
  `&scope=profile+email` +           // exactly what access is being requested
  `&response_type=code`;
window.location = authUrl;

// 2. The user logs in and approves on the PROVIDER's site, not the app's
// 3. The provider redirects back with a short-lived authorization code
// https://myapp.com/callback?code=abc123

// 4. The app's SERVER exchanges that code for an access token (never done in the browser)
const tokenResponse = await fetch("https://accounts.provider.com/token", {
  method: "POST",
  body: new URLSearchParams({
    code: "abc123",
    client_id: CLIENT_ID,
    client_secret: CLIENT_SECRET, // stays server-side, exactly like the JWT signing key in Chapter 108
    grant_type: "authorization_code",
  }),
});
const { access_token } = await tokenResponse.json();

    The user's credentials never pass through the requesting app at any point — they're entered directly on the provider's own login page, and the app only ever receives a token scoped to the specific permissions the user approved.

    Using the access token

    const profile = await fetch("https://api.provider.com/userinfo", {
  headers: { Authorization: `Bearer ${access_token}` }, // same bearer pattern as Chapter 108
}).then(r => r.json());

    Scopes limit what's shared

    A scope like profile+email in the example above tells the provider exactly which pieces of data the app is requesting access to — the user sees this list on the consent screen and can decline, so access is both limited and explicitly agreed to.

    Teaching note: OAuth, JWTs, encryption, and everything else in this part are individual tools. The closing security chapter pulls them together into a single practical checklist for shipping a real application.
    Chapter 110

    Security Best Practices

    This chapter closes Part XI with a consolidated checklist — not new material, but a summary of Chapters 101–109 organized as the questions worth asking before shipping any JavaScript application that handles real user data.

    A pre-launch security checklist

    • Output — is untrusted content ever inserted with innerHTML instead of textContent, or inserted without sanitizing (Chapter 101)?
    • State-changing requests — are cookies marked SameSite, and are CSRF tokens checked on requests that change data (Chapter 102)?
    • Input — is every field re-validated on the server, using an allowlist rather than a blocklist (Chapter 104)?
    • Passwords — are they hashed with bcrypt or an equivalent, never stored in plain text (Chapter 105)?
    • Access — does every endpoint check ownership, not just login status (Chapter 106)?
    • Transport — is the entire app served over HTTPS, with no mixed content (Chapter 107)?
    • Tokens — do JWTs expire, and are they kept out of localStorage (Chapter 108)?
    • Dependencies — has npm audit been run recently, with no unpatched high-severity issues?

    Security headers worth setting

    // A minimal set of response headers, conceptually
res.set({
  "Content-Security-Policy": "default-src 'self'",       // Chapter 101
  "X-Content-Type-Options": "nosniff",                    // stops the browser guessing file types
  "Strict-Transport-Security": "max-age=63072000",        // forces HTTPS on future visits
  "X-Frame-Options": "DENY",                               // blocks the page being embedded in an <iframe>
});

    Defense in depth

    No single control in this part is meant to stand alone — input validation, output escaping, authorization checks, and a Content Security Policy each catch what the others might miss, so that one mistake in one layer doesn't become a full breach on its own.

    Security is ongoing, not a checkbox

    New vulnerabilities are discovered in libraries and browsers continuously, so this checklist is a starting point revisited regularly — through dependency updates, periodic code review, and staying aware of how the threat landscape for JavaScript applications keeps changing.

    Chapter 111

    Clean Code

    Clean code is code written primarily to be read by other people — and by the same author again in six months — not just to be executed correctly once by the JavaScript engine covered back in Part VIII.

    Names should say what, not how

    // Unclear
const d = 86400000;
function calc(u) { return u.filter(x => x.a).length; }

// Clear
const MILLISECONDS_PER_DAY = 86400000;
function countActiveUsers(users) {
  return users.filter(user => user.isActive).length;
}

    A good variable or function name removes the need for a comment explaining it — countActiveUsers tells the reader what it returns without them needing to trace through the body first.

    Functions should do one thing

    // Doing too much at once
function processOrder(order) {
  validateOrder(order);
  const total = order.items.reduce((sum, i) => sum + i.price, 0);
  db.orders.save({ ...order, total });
  sendEmail(order.customerEmail, "Order confirmed");
  updateInventory(order.items);
}

// Split by responsibility -- each function is independently readable and testable
function processOrder(order) {
  validateOrder(order);
  const savedOrder = saveOrder(order);
  notifyCustomer(savedOrder);
  updateInventory(order.items);
}

    A function that validates, calculates, saves, emails, and updates inventory all at once is difficult to test in isolation (Chapter 116) and difficult to reuse — splitting it by responsibility makes each piece something a reader can understand on its own.

    Avoid deep nesting: prefer early returns

    // Deeply nested
function getDiscount(user) {
  if (user) {
    if (user.isActive) {
      if (user.orders.length > 10) {
        return 0.1;
      }
    }
  }
  return 0;
}

// Flattened with early returns
function getDiscount(user) {
  if (!user || !user.isActive) return 0;
  if (user.orders.length <= 10) return 0;
  return 0.1;
}

    Avoid magic numbers and strings

    // Magic value -- what does 3 mean here?
if (user.role === 3) { grantAdminAccess(); }

// Named, self-documenting
const ROLES = { VIEWER: 1, EDITOR: 2, ADMIN: 3 };
if (user.role === ROLES.ADMIN) { grantAdminAccess(); }
    Teaching note: Clean code is a set of habits; the next chapter, documentation, is what to write down when the code alone still doesn't explain the "why" behind a decision.
    Chapter 112

    Code Documentation

    Documentation captures the things clean naming (Chapter 111) can't — the reasoning behind a non-obvious decision, the shape of data flowing through a function, and how to use a piece of code without reading its entire implementation.

    JSDoc comments

    /**
 * Calculates the discounted price for a loyal customer.
 * @param {number} price - The original price in cents.
 * @param {number} orderCount - How many previous orders the customer has placed.
 * @returns {number} The discounted price in cents, rounded down.
 */
function applyLoyaltyDiscount(price, orderCount) {
  const discount = orderCount > 10 ? 0.1 : 0;
  return Math.floor(price * (1 - discount));
}

    JSDoc comments like this let editors show inline type hints and parameter descriptions on hover, and tools can generate browsable API reference documentation directly from them without a separate document to keep in sync.

    Comment the "why," not the "what"

    // Unhelpful -- just restates the code
// increment i by 1
i++;

// Helpful -- explains a non-obvious reason
// Skip the first result: the API always returns a stale cached entry in position 0
const freshResults = results.slice(1);

    Code already says what it does; a comment that just repeats that in English adds noise without value — comments earn their place by explaining something the code can't say on its own, like a workaround for an external system's quirk.

    A useful README structure

    ## Project Name
Short description of what this does and why it exists.

## Setup
npm install
npm run dev

## Environment variables
DATABASE_URL - connection string for Postgres
JWT_SECRET   - signing key for auth tokens (Chapter 108)

## Scripts
npm test     - runs the test suite (Chapter 115)
npm run build - produces a production bundle

    Keep documentation close to the code

    Documentation that lives far from the code it describes — a wiki page nobody remembers to update, for instance — drifts out of date quickly; comments and README files stored in the repository itself are far more likely to be updated in the same commit that changes the behavior they describe.

    Teaching note: Good documentation makes a codebase easier to read; a consistent style guide, covered next, makes it easier to read at a glance by removing pointless variation between files.
    Chapter 113

    JavaScript Style Guide

    A style guide is a set of agreed formatting and naming conventions applied consistently across a codebase — its value isn't that any one convention is objectively best, but that a team no longer wastes time debating tabs versus spaces in every code review.

    Naming conventions

    const userAge = 25;              // camelCase for variables and functions
function getUserProfile() {}     // camelCase for functions
class ShoppingCart {}            // PascalCase for classes (Chapter 82)
const MAX_RETRY_COUNT = 3;       // UPPER_SNAKE_CASE for true constants

    Prefer const, then let, never var

    const total = calculateTotal(items); // signals this value never gets reassigned
let attempts = 0;                     // signals this value will change
attempts++;
// var (Chapter 2) is function-scoped and hoisted in confusing ways -- avoid it entirely in modern code

    Automate formatting instead of debating it

    // .prettierrc
{
  "semi": true,
  "singleQuote": true,
  "trailingComma": "es5",
  "printWidth": 80
}

    Tools like Prettier apply a single consistent format automatically on save or commit, which removes formatting entirely from code review discussions — reviewers can focus on logic instead of arguing about where a brace goes.

    Linting catches more than formatting

    // .eslintrc (conceptually)
{
  "rules": {
    "no-unused-vars": "error",
    "eqeqeq": "error",       // require === over ==, from Chapter 4
    "no-var": "error"
  }
}

    Where Prettier handles how code looks, a linter like ESLint catches likely bugs and enforces the team's actual coding rules — the two tools are typically run together, one after the other.

    Consistency beats personal preference

    Whether a team prefers arrow functions or function declarations, single or double quotes, matters far less than that the whole codebase agrees on one choice — a mixed style is what actually slows readers down.

    Teaching note: A consistent, readable codebase is also easier to profile and optimize, since problems stand out more clearly against a uniform baseline — which leads into performance optimization next.
    Chapter 114

    Performance Optimization

    Performance optimization means measuring where an application actually spends its time or memory, then addressing that specific bottleneck — guessing at what's slow, without measuring first, routinely leads developers to optimize code that was never the problem.

    Measure before optimizing

    console.time("processData");
processData(largeDataset);
console.timeEnd("processData"); // processData: 842.31ms

// The Performance API gives finer-grained, production-safe measurements
performance.mark("start");
processData(largeDataset);
performance.mark("end");
performance.measure("processData", "start", "end");

    Browser developer tools also include a full Performance and Memory profiler capable of showing exactly which function calls consume the most time, which is almost always a better starting point than intuition.

    Debouncing and throttling expensive handlers

    function debounce(fn, delay) {
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delay);
  };
}

// Without debouncing, this fires on every keystroke -- with it, only after typing pauses
searchInput.addEventListener("input", debounce((e) => {
  fetchSearchResults(e.target.value); // an expensive network call, from Part VII
}, 300));

    Debouncing delays a function until activity has paused, which is ideal for search-as-you-type; throttling instead guarantees a function runs at most once per interval, better suited to something continuous like a scroll handler.

    Avoid unnecessary re-renders and DOM work

    // Inefficient -- triggers a layout recalculation on every iteration
for (const item of items) {
  list.innerHTML += `<li>${item}</li>`; // Chapter 43 -- reparsed and reflowed each time
}

// Efficient -- builds the structure once, touches the DOM a single time
const fragment = document.createDocumentFragment();
for (const item of items) {
  const li = document.createElement("li");
  li.textContent = item;
  fragment.appendChild(li);
}
list.appendChild(fragment);

    Every direct write to the DOM can force the browser to recalculate layout; batching changes into a DocumentFragment and appending once, as above, means that recalculation happens a single time instead of once per item.

    Lazy loading

    // Only load a heavy module when it's actually needed (Chapter 71's dynamic import)
button.addEventListener("click", async () => {
  const { generateReport } = await import("./reportGenerator.js");
  generateReport();
});
    Teaching note: Performance work is only trustworthy if it's verifiable — the same discipline of measuring before and after applies directly to the testing practices covered across the next three chapters.
    Chapter 115

    Testing

    Automated tests are code that checks other code — run in seconds, repeatedly, and without a human manually clicking through the application to confirm nothing broke; this chapter introduces the vocabulary and shape of testing before Chapters 116 and 117 go deep on two specific kinds.

    The testing pyramid

    • Unit tests — check one small piece of code (a single function) in isolation; fast, numerous, covered in depth in Chapter 116.
    • Integration tests — check that several pieces work correctly together (a function that calls a database); fewer, slower, covered in Chapter 117.
    • End-to-end tests — check a full user flow through the real, running application, such as an automated script that fills out and submits a signup form; the slowest and least numerous of the three.

    The "pyramid" shape describes the recommended proportion: many fast unit tests at the base, fewer integration tests in the middle, and only a handful of slow end-to-end tests at the top.

    Anatomy of a test

    import { test, expect } from "vitest";

test("adds two numbers correctly", () => {
  // Arrange -- set up the inputs
  const a = 2, b = 3;
  // Act -- run the code under test
  const result = add(a, b);
  // Assert -- check the result matches expectations
  expect(result).toBe(5);
});

    The Arrange-Act-Assert pattern shown here is the standard shape of nearly every test, regardless of the testing library or the kind of test: set up the situation, perform the action, then check the outcome.

    Why tests pay for themselves

    A test suite that runs in seconds catches a broken function immediately, before it reaches a real user — the alternative, discovering the same bug in production, typically costs far more time to diagnose and far more trust to repair.

    Teaching note: With the vocabulary in place, the next chapter puts unit testing into practice with a real testing library, followed by integration testing for the pieces that only fail when combined.
    Chapter 116

    Unit Testing

    A unit test verifies a single function or module in isolation from everything else — the fastest, most numerous layer of the testing pyramid introduced in Chapter 115, and usually the first tests written for any new piece of logic.

    Writing a first unit test

    // discount.js
export function applyDiscount(price, percent) {
  if (percent < 0 || percent > 100) throw new Error("Invalid percent");
  return price * (1 - percent / 100);
}

// discount.test.js
import { test, expect } from "vitest";
import { applyDiscount } from "./discount.js";

test("applies a valid discount correctly", () => {
  expect(applyDiscount(100, 20)).toBe(80);
});

test("throws on an invalid percentage", () => {
  expect(() => applyDiscount(100, 150)).toThrow("Invalid percent");
});

    Testing both a normal case and an edge case, like the invalid percentage above, is standard practice — the edge case test would have caught a bug the happy-path test alone never exercises.

    Isolating a unit with mocks

    import { test, expect, vi } from "vitest";

test("sends a welcome email on signup", async () => {
  const mockSendEmail = vi.fn(); // a fake function that just records how it was called
  await signupUser({ email: "a@b.com" }, mockSendEmail);
  expect(mockSendEmail).toHaveBeenCalledWith("a@b.com", "Welcome!");
});

    A mock replaces a real dependency, like an email service, with a fake version that records how it was called — this keeps the test focused only on signupUser's own logic, without actually sending an email or depending on a network call from Part VII.

    Test coverage

    npx vitest run --coverage
// File          | % Stmts | % Branch |
// discount.js   |   100   |    100   |

    Coverage measures how much of the code a test suite actually exercises, but 100% coverage is not the same as a bug-free application — it only means every line ran at least once, not that every meaningful combination of inputs was checked.

    Test-driven development (TDD)

    TDD is the practice of writing a failing test first, then writing just enough code to make it pass, then refactoring (Chapter 111) with the safety of that test in place — a discipline some teams follow strictly and others use more loosely.

    Teaching note: Unit tests assume dependencies work correctly and mock them away, as shown above; the next chapter, integration testing, is precisely what checks that assumption — that the real pieces actually work together.
    Chapter 117

    Integration Testing

    An integration test checks that several real pieces of a system work correctly together — a route handler that actually talks to a real (test) database, for instance — catching bugs that unit tests, with their mocked dependencies (Chapter 116), are structurally unable to see.

    Why unit tests alone aren't enough

    // A unit test with a mock database passes even if the real SQL query is wrong
test("getUser calls the database with the right id", () => {
  const mockDb = { query: vi.fn().mockResolvedValue({ id: 1, name: "Ana" }) };
  getUser(mockDb, 1);
  expect(mockDb.query).toHaveBeenCalled(); // doesn't verify the query is actually correct SQL
});

    Because the mock simply records that it was called, this test would still pass even if the real SQL query contained a typo — an integration test that runs against a real (test) database is what actually catches that.

    Testing an API endpoint end-to-end within the server

    import { test, expect, beforeEach } from "vitest";
import request from "supertest";
import { app } from "./app.js";
import { resetTestDatabase } from "./testUtils.js";

beforeEach(async () => {
  await resetTestDatabase(); // a clean, known state before every test
});

test("POST /users creates a new user", async () => {
  const response = await request(app)
    .post("/users")
    .send({ email: "new@example.com", password: "securepass123" });

  expect(response.status).toBe(201);
  expect(response.body.email).toBe("new@example.com");
});

    Resetting the test database before every test, as beforeEach does here, keeps tests independent of one another — a test that depends on data left behind by a previous test is a common source of tests that pass alone but fail when run together.

    Using a real (but isolated) test database

    Integration tests should run against a dedicated test database — never a production or shared development database — so that tests can freely create, modify, and delete data without any risk to real user information.

    Balancing speed against realism

    Integration tests are inherently slower than unit tests, since they involve real I/O like database queries, so most teams write many focused unit tests and a smaller number of integration tests for the critical paths where components genuinely need to be checked together.

    Teaching note: With a codebase that's clean, documented, tested at multiple levels, and reasonably fast, it's ready to ship — the next chapter covers what actually getting it in front of users involves.

    Deployment

    Deployment is the process of taking finished, tested code and making it available to real users — a step that, done well, is boring and repeatable rather than a stressful, manual, late-night event.

    Building for production

    npm run build
// Produces optimized, minified output -- typically in a dist/ or build/ folder
// Minification strips whitespace and shortens variable names to reduce file size
// Bundling (Chapter 71) combines many modules into fewer files to reduce requests

    Environment-specific configuration

    // .env.production (never committed to version control)
DATABASE_URL=postgres://prod-server/app

    # .github/workflows/deploy.yml (conceptually)
on: push

  deploy:

    Rolling back

    Every deployment process needs a fast way to undo a bad release — whether by redeploying the previous build or through a feature flag that disables the new code path — since even a well-tested change can behave unexpectedly against real production traffic and data.

    State management, drawing on Part IV and VIII

    // state.js
let tasks = [];
const listeners = new Set();

    // api/tasks.js
export async function createTask(text) {
  const errors = validateTaskInput({ text }); // Chapter 104
  if (Object.keys(errors).length) throw new Error("Invalid task");

  const response = await fetch("/api/tasks", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${getStoredToken()}`, // Chapter 108
    },
    body: JSON.stringify({ text }),
  });
  if (!response.ok) throw new Error(`Request failed: ${response.status}`);
  return response.json();
}
